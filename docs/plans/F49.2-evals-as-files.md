# F49.2 The cook's eval as files

> **What this answers:** how an eval stops being a C# class and becomes a folder of files beside the identity it
> proves (`eval.json`, the dataset, the rubric, the labels, the transcripts), read by the harness and run by the
> runner with nothing of its own in C#. The second child of [F49 Evals as content](F49-evals-as-content.md).
> Branch `feature/F49.2-evals-as-files`. The page with the diagrams drawn: <https://claude.ai/artifact/UME4Qwiws8cVjELRf5sRCU>.

Status: **approved 2026-10-30** (Louis: "just go down the order"); all six findings picked on their cards by 16:03, each
on the recommended option, recorded at the end.

## The goal, in Louis's words

"A new eval must only be a JSON file" (2026-10-30). After F49.2, an eval that uses checks the catalogue already
has is a folder with no C# in it, and the cook's and the routing's evals are the first two.

## Context: what F49.1 left, and what this takes on

F49.1 made a check a catalogue entry: a type in kebab case, a typed settings record, `CheckCatalog` to find it.
Nothing names an entry from a file yet. `CookEval` and `RoutingEval` are still C# classes in
`evals/louis-agent.evals.puls` that build their checks by hand, read their dataset from `Dataset/` beside them,
embed the judge's prompt, and say what a turn's facts are through `PulsTurnFacts`.

The parent plan's done-when for F49.2: **`evals/louis-agent.evals.puls` is empty and the cook's replayed run
grades the same as the baseline** (`puls-cook 5d1fd231c9b1`, `puls-routing 0d3b95e093a6`).

## Design: what changes

Keep it simple (ADR 0055): the dataset's files don't change shape, the protocol doesn't change, and a check keeps
its name and version, so a stored run and the trend read the same. Four things change:

1. **An eval is a folder with an `eval.json`.** The file names the eval, its version, what it proves, its modes
   and its checks by type with their settings; the dataset, the rubric, the labels and the transcripts sit beside it
   as they do today. Read strictly through records (`EvalFile`, `EvalJson.Strict`, ADR 0041): an unknown field, a
   missing one or a null is refused naming the file and the field, as a check's settings are.
2. **`FileEval` is the one `IEval` built from a folder.** It loads the dataset with today's loader, builds each check
   through the catalogue (the entry's type, a `name` where the file keeps an old name), and builds the modes from
   the file. The C# evals go: `CookEval`, `RoutingEval`, and the stub becomes a folder too, so the runner has no
   C# eval left and the template is a folder a person copies.
3. **Three entries the files need.** `routed-to` (the expected role from a scenario key; a mode without a delegating
   toolset answers itself), `judge` (a rubric file as the system prompt, the ask from the scenario's expected keys,
   one yes-or-no verdict with a reason) and `human` (a person's review of a named judge). They complete the general
   checks; the cook's own checks become entries the identity lists (finding D), and the shops ones move to the
   pack in F49.3.
4. **The runner finds eval folders and gathers the catalogue.** Every `eval.json` under the eval files beside the
   runner is an eval (finding F), and the catalogue is the general checks plus each owner's list, gathered in the
   one place that knows them (ADR 0027). `IEvalSet`, `EvalSets` and `EVALS=puls`'s enum go; `EVALS=` filters by
   the identity the file names.

### The file

```json
{
  "schema_version": 1,
  "name": "puls-cook",
  "identity": "puls",
  "version": 11,
  "proves": "Puls gives a meal for the people asked, with estimates and the shop's branches, in Afrikaans or English.",
  "manual": "manual.md",
  "modes": [
    { "name": "puls-tools", "role": "puls/voice-af", "toolsets": ["web", "shops"] },
    { "name": "puls-cook", "role": "puls/voice-af", "toolsets": ["specialists", "web"] }
  ],
  "checks": [
    { "type": "no-error", "name": "cook-no-error" },
    { "type": "routed-to", "parameters": { "expected_key": "routes_to", "delegating_toolsets": ["specialists"] } },
    { "type": "within-budget" },
    { "type": "estimates-at-shop" },
    { "type": "untooled-shops" },
    { "type": "recipe-image" },
    { "type": "serves-as-asked" },
    { "type": "meal-for-people", "parameters": { "rubric": "rubrics/meal-for-people.md", "version": 2 } },
    { "type": "human", "parameters": { "reviews": "meal-for-people" } }
  ]
}
```

`name` on an entry is only there to keep a name a stored run already carries (`cook-no-error` is the general
`no-error`); a new eval leaves it out and the name is the type (F49.1's note). `parameters` is left out where the
record has only defaults. The `proves` text moves out of `PulsEvalMessage` into the file: it is content, not a
message the code gives (ADR 0009 is about the code's texts).

## Verification

- `ArchitectureTests`: the identity references core and the checks contract, never the harness; the harness
  references no identity.
- `EvalConformanceTests` run on `FileEval` for every folder found, so a stray file or a bad check order (the
  `human` before its judge) stops the runner's start as today.
- The reference and known-bad transcripts of both evals grade the same before and after (steps 6 and 8), and the
  baseline runs replay the same (step 8). No live run in the plan; one live cook run at the end only on Louis's go.

## Done when

A new eval that uses existing checks is a folder of files with zero C#; `evals/louis-agent.evals.puls` is gone;
the cook's and routing's evals run from `identities/louis-agent.identity.puls/Evals/` and grade the same as their
baselines.

## Findings (one card each, in this order)

**A. What the eval's version looks like** (parent finding 4; **picked 2026-10-30 15:45: an integer as today**). Options: (1) **an integer as today**, bumped by hand
when a scenario, a mode or a check changes, with the dataset's content hash recorded beside it as today
(recommended: nothing in the trend, the baseline or the portal changes, and the person says what a bump means in
`dataset.json`'s `changes`); (2) inspect_evals' `N-X` (the eval's and the dataset's numbers in one string; costs a
new parser and a wire change); (3) a hash of the folder (nothing to bump, but a comment change is a new version and
the trend can't tell a small change from a big one).

**B. Where a turn's facts come from** (parent finding 5; **picked 2026-10-30 15:46: the harness reads them**). Options: (1) **the harness reads them from the events for
every eval** (recommended: `TurnFacts.Of(turn)` in the contract from `EngineEvents`, the hosts read from the tool
inputs' URLs as `ToolHosts` does; `IEval.TurnFactsOf` gets that as its default, the stub keeps its canned override;
`PulsTurnFacts` and most of `TurnView` go); (2) a named extractor in the catalogue (`"turn_facts": "puls"`; one more
registry for one implementation); (3) the identity's own C# hook (a file can't name it, so a new eval would need C#).

**C. The routing eval's baseline mode** (**picked 2026-10-30 15:47: the file lists the toolsets**), today "every toolset the instance has but the delegating ones", read from
the instance at run time. Options: (1) **the file lists the toolsets** (recommended: a run's mode line already
records exactly this list, so the file says what ran; a test in the identity's tests holds the list equal to the
instance's toolsets minus the delegating ones, so drift fails a test, not a run); (2) a mode in the file says
`"toolsets": "instance"` with `"without": [...]`, resolved at run time (a second way to say a mode, for one eval);
(3) the routing eval stays C# (breaks the done-when).

**D. Where the cook's own checks live** (`within-budget`, `serves-as-asked`, `recipe-image`, the three shops ones
until F49.3, `meal-for-people`; **picked 2026-10-30 15:48: the identity project**). Options: (1) **the identity project, `Evals/Checks/`, listed by `PulsChecks.All`**
(recommended: the identity owns what proves it, ADR 0027, and the composition gathers the list as it gathers packs;
the identity references the checks contract, one reference; core's `IIdentity` can't name `ICheckType`, so the
composition reads `PulsChecks.All` directly, as it reads `PulsIdentity`); (2) `evals/louis-agent.evals.puls` stays
as "Puls's checks" (two homes for one eval, and the parent's done-when fails); (3) all into packs now (the cook's
non-shop checks have no pack until F35's recipes pack; blocks on F35).

**E. The judge's context** (**picked 2026-10-30 16:02: a generic judge, and the cook keeps its own over it**). Today `CookAsk` tells the judge the people (the last number asked up to the turn) and
the town, read by the cook's own code. Options: (1) **a generic `judge` entry in the harness for new evals, and
the cook keeps `meal-for-people` as its own entry over it, with `CookAsk`** (recommended: the 36 labels and the
calibration stay exactly as measured; a new eval gets a judge with no C#; the cook's can move to the generic one
later, with a re-calibration, when a plan wants it); (2) only the generic judge, the ask = every expected key as
`key: value` (simplest, but the per-turn `serves` reading goes and the calibration must be re-run, a paid judge
run over 36 answers); (3) no generic judge yet, every judge an identity's entry (a new eval with a rubric would
need C#, against the goal).

**F. How the runner finds eval folders** (**picked 2026-10-30 16:03: a scan for `eval.json`**). Options: (1) **a scan: every `eval.json` under `EvalFiles/` beside the
runner is an eval, its identity from the file** (recommended: a new eval is a folder dropped in, zero C#; the
identity's project copies `Evals/**` to the output as the eval project does today; `EVALS=` filters by identity);
(2) the identity lists its folders in C# (`PulsEvals.Folders`; one line per eval, but a line of C#); (3) a path in
`EVAL_FILES=` (works for a hosted instance later, F49.5, but a second way for the same thing now).

## Approved during the build

- **2026-10-30, step 1:** the reader refuses what Louis's brief lists (no file, unreadable, another schema version,
  no modes, no checks, a mode or a check name twice), and one more: a file whose JSON is `null` holds no eval
  (`EvalFileMessage.Empty`), as `CheckType` refuses null settings. The records sit in one file, `Files/EvalFile.cs`,
  as the file's one shape. Its test names Puls's eval, modes and toolsets with the sample names, as
  `RepeatedNameTests` (ADR 0043) asks of the harness's tests; it was fixed in its own commit after step 1.
- **2026-10-30, step 2:** Puls's settings are `["specialists"]` only (Louis's pick, recorded in the step's row).
  `RoutedToCheck.ByScenarioKey` builds the same check in C#, which `CookEval` and `RoutingEval` use until their
  files replace them (steps 6 and 8); `ExpectedRoute.Of` stays, the cook's expectations and the datasets' tests read
  it.
- **2026-10-30, step 3 (Louis's three picks):** an entry is built with a `CheckContext(Folder, Before)` beside its
  settings (a Parameter Object, changed through Rider's *Change Signature*), so `judge` reads its rubric from the
  eval's folder and `human` finds its judge among the checks built before it. The judge is told only the keys its
  settings list (`"ask": ["serves"]`, its expected keys), not every key: the cook's lesson that a model can't misuse
  what it isn't told. Every rubric asks for `{"pass": true | false | null, "reason": "…"}`. The judge lives in
  `Grading/Models/Rubrics/` (`Models/` was at five files); it exposes its `Rubric`, and the review makes its question
  from it, so `Human/` depends on the judge and not back.
- **2026-10-30, step 4 (Louis's two picks):** an entry's `name` is a renaming Decorator, `Grading/NamedCheck`, which
  `FileEval` wraps around the one check its file renames; `human` looks through it to find a renamed judge. The
  manual's path is `{source}/{manual}`, where the caller (the runner, step 5) gives the folder's path from the
  repository root. A turn's facts are `TurnFacts.Of(turn)` for every eval (finding B), the default of
  `IEval.TurnFactsOf`: the hosts are those of the URLs the tools were given, so the cook's shop hosts (from Puls's shop
  table) are left for step 8 to settle. The test builds its sample folder in temp, as the loader's tests do; the
  template becomes a folder in step 9.
- **2026-10-30, step 5 (Louis's three picks):** `IEvalSet`, `EvalSets` and `EvalSetKind` stay until step 8: Puls's
  evals are C# until steps 6 and 8, so the runner finds the sets as before and the folders beside them, and `EVALS=`
  picks both (a folder by the identity it names). Every eval project's data item copies every file under `Evals/`
  that isn't code to `EvalFiles/{its path from the repository root}/...`, so a copy's path below `EvalFiles/` is the
  folder's source; `EvalFiles` (for the C# evals) reads the same layout. The stub stays `StubEval` in C#: it proves the
  portal with canned facts and a canned client, and the template (step 9) is the example folder instead.
