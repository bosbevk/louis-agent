## Context

**What Louis asked:** an address reaches an agent on this instance (F127.3.1) or on someone else's server:
`{peer}:{identity}` asks the identity on the server named `peer`, with that server's own key; the other side's
identities are read from its `/v1/identities` before an address is trusted; an unknown peer, a refused key and a
server that is down each give the model a reason.

**What exists:** `AGENT_PEERS` names servers (`self=http://localhost:8080` on the site); `AskAgent` resolves an address
against this instance's identities and asks the one peer there is; every request to a peer carries this instance's
`AGENT_API_KEY`; an identity's `Calls` list who it may ask, checked in code and listed in its prompt.

**What this child is not:** no agent on louis-agent.dev asks another server yet, so none of the site's identities gets
a peer address, and the privacy terms gain no line until one does (Q5).

## Design

### What changes, in plain words

- **An address may name its server:** `partner:shop` or `partner:shop.cook`, read once into `AgentAddress` (its
  `Peer`); without one it is this instance, as before.
- **A key per peer:** `AGENT_PEER_KEYS` (a secret, `name=key` pairs) beside `AGENT_PEERS`; every request to a peer
  carries that peer's key, and this instance's own key when the peer has none (Q1).
- **The other side's identities:** before a peer address is trusted, its server's `GET /v1/identities` is read with
  its key and kept ten minutes (Q2); an identity it doesn't list is refused, naming the ones it does.
- **The reasons:** a peer not in `AGENT_PEERS`, a key the peer refuses (401), a peer that doesn't answer, each a line
  the model can pass on.
- **The model says so first:** the `agents` toolset's guide says a peer address leaves this hosting, so the agent
  tells the person in one line before it asks (Q3).

## Steps

Each step test first, one commit, `core.tests` when a folder or a name is added.

1. **The plan**, its pictures drawn.
2. **An address names its server:** `AgentAddress` reads and writes `{peer}:{identity}[.{role}]`, a peer a name like
   any other; `Calls` may list one. Tests: `AgentAddressTests`, `AgentCallsTests`.
3. **A key per peer:** `AGENT_PEER_KEYS` read as a secret; `PeerHttp` sends each request with the key of the peer it
   goes to, this instance's own when that peer has none; the secrets examples name it. Tests: the options, `PeerHttp`.
4. **The other side's identities:** `PeerIdentities` reads a peer's `/v1/identities` with its key and keeps the list
   ten minutes; a peer not in `AGENT_PEERS`, a refused key, a peer that doesn't answer and an identity it doesn't
   list each give a reason. Tests with a stub server.
5. **`AskAgent` asks the address's server:** a peer address goes to its peer once its identities list it; a local one
   resolves as before; `ReadAgentWork` reads from the same server. Tests: `AskAgentTools` with stubs.
6. **The model says so first:** the `agents` toolset's guide: an address with a server leaves this hosting, so say so
   in one line before asking. The goldens regenerated.
7. **Two servers:** two API hosts in one test, the first asking an identity on the second through the real HTTP
   pipeline with the second's own key; a wrong key and an unknown identity give their reasons. No model cost.
8. **The docs:** ADR 0117's record, core's and the API's design docs, the settings, the work log, the write-up, the
   full suite, this plan deleted.

## Verification

- **Each step:** the tests of what it touches; `core.tests` for new folders and names.
- **Two servers:** step 7's test, the HTTP pipeline real on both sides; no paid run, since no site agent asks a peer.
- **Full suite** once, in step 8.

## Concepts, and where they sit in GOAL.md

- **Protocols** (skill 11): one agent API reaching another, with an address, a key and a directory read first.
- **Safety** (skill 15): a key per peer, an allow-list in code, and the person told before their words leave.
- **Multi-agent orchestration** (skill 10): agents on different servers, asked the same way.

## Claude's picks (unattended), each of three

| # | Question | Pick | The other two |
|---|---|---|---|
| Q1 | The shape of a key per peer | **`AGENT_PEER_KEYS` (a secret, `name=key`), the peer's key on every request to it, this instance's own when it has none** | The key in `AGENT_PEERS`' URL: a secret in a setting that isn't one · One key for every peer: one leak opens them all |
| Q2 | How long a peer's identities are kept | **Ten minutes, in memory** | Read on every ask: a round trip each time · Listed by hand in a setting: drifts from the other side |
| Q3 | What the person is told | **The agents guide: say in one line that the question goes to another company's server, before asking** | A badge in the page: the web learns peers · Only the privacy terms: nobody reads them mid-chat |
| Q4 | Where a peer address may be asked from | **An identity's `Calls`, as a local one** | A setting adding calls: the allow-list leaves the code · Any peer address in `AGENT_PEERS`: the model chooses |
| Q5 | The privacy terms' line | **Waits until a site agent asks another server** (none does: writing it now would describe what the site doesn't do) | Written now as a possibility: a claim the site doesn't make true · Never: the person must be told when it ships |
| Q6 | How the plan's *done when* is shown | **Two API hosts in one test, the HTTP real, no model** | A second container and a live guide run: the guide would have to ship a peer address · A stub peer only: the other side's door and key are never exercised |
