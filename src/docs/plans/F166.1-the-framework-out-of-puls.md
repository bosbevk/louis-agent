# F166.1 The framework's parts out of demos/puls

A plan, F166's first child: the framework takes back from `demos/puls` what is its own, the API's tests and the
deploy that releases its two sites, so Puls can later leave without taking any of the framework with it. Nothing
changes in what the API or the sites do.

## Context

**What Louis asked.** F166's parent plan names this child (2026-11-19, "we need to move it"). His picks of that
day for it, each of three options after research:

| # | The choice | His pick |
|---|---|---|
| 1 | What the API's tests run on once Puls leaves | A: a test agent of their own, from the framework's `FakeIdentity` on framework packs, over a site's identity (B) or leaving the tests with Puls (C) |
| 2 | The Puls-era Azure parts | A: only what releases the two sites moves, without the `infra`, `vm` and `sql-access` verbs; the Bicep build and the VM's files stay, to leave with Puls, over moving all of it (B) or a new Bicep of what exists (C) |
| 3 | Which runner the API's integration tests start | A: a small test runner program on the framework's runner library, over the stand-in (B) or leaving them with Puls (C) |

**What was looked up.** `ApiTestHost` (`louis-agent.api.testing`) builds the in-memory API on `PulsIdentity` with
the web, where-to-buy, shop-prices, recipes and calculator packs; about 360 tests run on it, and eleven files of
`api.tests` and six of `api.evals.tests` name Puls's parts. `FakeIdentity` (in `louis-agent.testing`) and the tests'
own `acme` business on the calculator already exist. `RunnerBuild` finds `louis-agent.puls-eval-runner`'s dll by its
path under `demos/puls/hosts`, and eight integration tests start it; `StandInBuild` finds the tests' stand-in the same
way. The framework's runner is a library, `src/evals/louis-agent.evals.runner`. A release reads Azure's recorded
deployment outputs, not the Bicep file, so the script runs without it. The trust page names
`demos/puls/deploy/azure/ARCHITECTURE.md` and `README.md` as the files behind two of its facts, and
`deploy-puls.yml` is named in the deploy README, the deployment view, ADR 0097, check-a-page and the workflow test.

**Not confirmed.** Which of the API's tests rely on something only Puls's identity had (a specialist, a role, a
prompt). Step 1 finds each, and gives the test agent that shape or, where the test really tested Puls, keeps it for
Puls's repository.

## Design

### The shape, in plain words

**A test agent the framework owns.** `TestAgent` in `louis-agent.api.testing` is a `FakeIdentity` with the roles and
specialists the API's tests need, on the web, calculator and `TestTools` packs. `ApiTestHost` builds on it; a test
that adds an identity or a pack still can.

**A test runner the framework owns.** `louis-agent.api.test-runner` is a program of a few lines on
`louis-agent.evals.runner`, with the test agent and a sample eval, and `RunnerBuild` finds it as it found Puls's.

**Then the moves.** The five test projects and the runner go to `src/tests/hosts/`. `deploy.ps1`, without its three
dead verbs, goes to `src/site/deploy/azure/` beside the two yamls, with its README, architecture page and pictures.
The tests of the script, the yamls, the workflow and the forwarded headers go with the site's tests; the tests of
the Bicep build and the VM stay with Puls. The workflow becomes `deploy-sites.yml`.

### What is reused

`FakeIdentity`, `TestTools`, the `acme` business, the web and calculator packs, `louis-agent.evals.runner`, the
stand-in's pattern for a small program in the tests, and the existing deploy script and docs, moved. No new package.

## Steps

Each is one commit with its test, written first and seen failing where it changes behaviour, and a stop after each.

1. **A test agent.** `TestAgent` and `ApiTestHost` on it. *Test:* a rule test that `louis-agent.api.testing` and the
   API's tests reference no project under `demos/`, seen failing first.
2. **The tests that named Puls.** Each of the seventeen files moved onto the test agent, or, where it tested Puls
   itself, set aside for Puls's repository and named in the step. *Test:* the rule test now passes for the unit tests.
3. **A test runner.** `louis-agent.api.test-runner` with a sample eval; `RunnerBuild` finds it; the eight
   integration tests start it. *Test:* the rule test passes for the integration tests too.
4. **The test projects move** to `src/tests/hosts/`, with the solution, CI and the two build-path finders. A pure
   move. *Test:* every moved test passes where it now stands.
5. **The deploy script moves** to `src/site/deploy/azure/`, without `infra`, `vm` and `sql-access`. *Test:* the
   deploy tests hold its new path and that the three verbs are gone.
6. **Its docs move** with it, the README, ARCHITECTURE.md and their pictures, and every link to them, the trust page's
   two facts among them. *Test:* the docs' link tests and the trust page's facts test.
7. **The deploy's tests move** to the site's tests; the Bicep and VM tests stay with Puls. *Test:* they pass there.
8. **The workflow renamed** `deploy-sites.yml`, and every place that names it. *Test:* `DeployWorkflowTests` on the new
   name.
9. **The docs, the write-up, the plan folded.** The API's and the sites' design docs, the repo map, the tests doc.

## Verification

The touched tests per step; before the pull request, `main` merged and the full unit suite. After the merge, the
release runs from the renamed workflow and both sites stay healthy. No paid run.
