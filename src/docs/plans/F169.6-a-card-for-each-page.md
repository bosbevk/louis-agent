# F169.6 A card for each page

A plan: what a shared link to the framework's site shows, as the design review's tenth pick asks. Each of the
nine pages gets a share card of its own, drawn in flat by the repo's card tool and kept as a file, and the host
names that file in the page's head. Every picture gets a description. It is the sixth child of
[F169 The framework's site, as the design review picked it](F169-the-design-reviews-picks.md), and it has nine
steps.

![F169.6 at a glance: the tool draws nine cards and keeps them as files, the host names a page's own card in its head, every picture says what it shows, and a test holds each card to its page](diagrams/F169.6-a-card-for-each-page-overview.svg)

## Design

### 1. What a shared link shows today

A platform that shows a card for a link reads the page's head and runs no script. So the host writes the head:
`PageShell` fills the site's `index.html` with the page's title, description and address. It does not touch the
picture. The framework's `index.html` names louis-agent.dev's picture, with a note that says the picture reads
"Build agents, not infrastructure". It does not. So all nine pages show the business site's card, whose slogan
speaks to a business owner and whose address is another site's.

No picture on any of the four sites says what it shows. The protocol asks for that line, and X reads it for a
person who can't see the picture.

### 2. The two cards

Both are 1200 by 630 points, the shape Facebook asks for, drawn at twice that, 2400 by 1260 pixels, as today's
card is. Both are in flat's light look, the look the site opens in.

A page's card has the site's name at 44 points, the page's name at 112, the page's heading at 44 in the second
ink, and a grey band along the foot with the page's address in Geist Mono. The site's card, which the Overview
wears, has the name at 132, "The C# AI agent framework" at 56 and the site's address on the same band.

The name on a card is a photograph of the site's own name, taken from the running site's header, enlarged, alone
on nothing. Today's tool photographs the glass ball the same way, and for the same reason: what the site draws
changes. Between the review and today, F169.3 made the o in flat smaller, from half the letters' size to .41 of
it. A card that drew its own name would already be wrong.

The grounds and inks are flat's light values, written in the card's page as today's card writes its own. A test
holds each colour in the card's page to flat's light sheet, so a changed theme value fails until the card's page
follows.

Every word starts 128 points from the left, and none may end past 1072. That is the middle 944 points, what a cut
to 3 to 2 keeps. The tool measures where a card's words end before it writes the card, and writes none that
runs past.

![The parts and their tests: the page shell takes a page's card, PageCards finds it by where its file is, and the tool's five new parts read, draw and check a card](diagrams/F169.6-a-card-for-each-page-interface-design.svg)

### 3. Where the files are, and how the host finds them

The site's own picture is `social-card.png` in the site's web root, as louis-agent.dev's is. A page's card is in
`social-cards/`, named for the page's address: `/getting-started` wears `social-cards/getting-started.png`, and
its description is `social-cards/getting-started.txt`. The framework's site holds nine pictures and eight text
files. The site's own picture has its description in `index.html`, where its address is.

In the host, a new `PageCards` answers one question: this route's card, or none. It looks in the site's web
root, which the page handler already reads `index.html` from. A picture with no text file beside it is not a
card, so a picture never shows with another picture's words. The root has none, since it wears the site's own.
What it found for a route it keeps, as the handler keeps a rendered page. The handler asks it with the route of
the page it matched, never with the address that was asked for, so a section's address gets its page's card and
nothing a visitor types reaches the file system.

`PageShell.Fill` takes the card beside the page. With a card, it writes the picture's address, absolute on the
site's own address, and its description. With none, it leaves both as the file has them. The two size tags stay:
every card of a site is one size, and a test holds each picture to the size its `index.html` says.

The shell replaces a tag the file has and adds none. So each site's `index.html` gains the description's tag, and
the rule that already asks six tags of every site asks for this seventh.

### 4. A card kept true to its page

A card is a picture of words, and those words are the page's. When a heading changes, the card goes on saying
the old one. His pick closes that with what the files already hold. The text file's words are the card's words,
in one line: the site's name, the page's name and the heading, as in "louis-agent: Getting started. Your agent,
in two lines." The tool writes that line and the picture in the same run.

A test in the framework's site's tests then draws each of the eight pages as the host draws it, and holds the
page's text file to the page's name and heading. A changed heading fails the test, and its message says to run
the tool. The same test file holds that every page has its picture and its words where the host looks, that each
picture is the size the head says, and that each is under WhatsApp's 600 KB.

The test reads the host's rule and the tool's output together. That matters because the tool and the host each
know the folder's name and how a file is named, and neither references the other. The test is what holds the two
to one rule.

### 5. The tool

The card tool is `src/tools/LouisAgent.FilmExport`. Its `social-card` command starts louis-agent.dev, photographs
the glass ball and writes that site's card. It gains a second command, `framework-cards`.

The new command starts the framework's site instead. It reads the site's pages from the site's own
`sitemap.xml`, which a test already holds to the pages. For each page it asks the running site for the page and
reads two things from the head and the words the host wrote: the title, from which it drops the site's name as
the host's breadcrumb does, and the first heading. It photographs the name once at each of the two sizes. Then it
lays each card out, checks it, photographs it and writes its text file.

It checks two things before it writes a card, and stops with a plain message when one fails. The card's type
must have loaded: a card drawn while Geist was missing looks nearly right and is wrong. And the words must end
inside the middle.

### 6. The main case, and what is in memory

handler finds the page for the address and asks `PageCards` for its card. The shell writes the head with the
page's own picture and its description. The crawler reads the head and fetches the picture, which the site
serves as the file it is.

## Concepts

The write-up belongs to skill 20, extensibility, in [the goal's skill map](../GOAL.md). Steps 3 and 4 are
convention over configuration: the host gives a page its card because a file is where the rule says it is, so a
site gains a card with two files and no line of code, and the price is a rule a person has to know. Steps 5 to 7
show how to put a browser to work without letting it into the tests: everything that can be decided without one
