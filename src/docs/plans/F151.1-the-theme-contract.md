# F151.1 The theme contract

A plan: how the framework's web comes to know what a theme and a style are, before any theme exists. It is the
first of the eight children of [F151 Two themes, each light and dark](F151-themes-and-styles.md), which says what
was decided and why. This file says what this child builds, then gives its eight steps, each with its own
picture.

## Context

F151 gives a visitor two themes, glass and flat, each light and dark, and lets them pick. A theme is a package of
values. For that to work the framework's web has to say three things first: what a theme is and how a site names
one, which names a theme must set, and how the page says which theme and style are on. That is this child. It
names no theme itself, so when it is merged every page looks exactly as it does today.

Louis's words for the whole feature are in the parent. The ones that shape this child are "each theme in it's
own package which then gets wired into core.web" and "the user picks and the browser rememebrs".

Before this plan was written the code was read for what is there. A site names its areas in one call, and a
library adds its own with `SiteAreasBuilder.Add`. The admin's home card was added as one more slot on `SiteArea`,
which is the nearest solved problem and the shape this child copies. The framework's colours are named in
`Styles/web/settings/_colours.scss`. A script every site lists in its head, `wwwroot/js/first-paint.js`, already
applies what the browser remembers before the first paint. Scripts here are tested by reading them, as
`AgentBarMotionTests` reads the bar's. The code-review demo's theme picker checks an id against lower-case
letters, digits and hyphens before it loads anything by that name.

## Design

### 1. What a theme and a style are

A theme has an id, which is written into the page and into the stylesheet, and a name a person reads on the
switch. A style is one of two: light or dark. A third small type holds what the C# side and the browser side must
agree on: the two words the browser remembers under, the two attributes on the page, and that a first visit is
light.

![An area may carry a theme, the areas list the themes in the order named, and a helper for tests reads a theme's sheet](diagrams/F151.1-the-theme-contract-interface-design.svg)

The members shown on `SiteArea`, `SiteAreas` and `SiteAreasBuilder` are the ones the code has today, with `Theme`,
`Themes` and `DefaultTheme` added.

### 2. Where each part goes

The contract is four things in `louis-agent.web` and one helper in the tests' shared library.

![The types, the slot, the surface names and the first-paint script are in the framework's web, held by a helper and a rule test](diagrams/F151.1-the-theme-contract-architecture.svg)

### 3. The main case

A site starts and names its areas. None of them is a theme yet, so the list of themes is empty and there is no
default. A page opens, the script finds nothing remembered, and the page keeps what its file wrote.

![A site names its areas with no theme among them, and a page opens with the style its file wrote](diagrams/F151.1-the-theme-contract-communication-a-site-starts-and-a-page-opens.svg)

The slot's own test is the one place two themes are named in this child, through two made-up areas.

![In the slot's test two areas carry a theme and one carries none, and the first theme named is the default](diagrams/F151.1-the-theme-contract-objects-in-memory.svg)

### 6. What is reused

The slot follows the admin card's on `SiteArea`. The style is an enum parsed once with `SettingChoice.TryParse`
and written with `.Wire()`, from `louis-agent.choices`. A refused id says so through the message enum and a holes
record, as the admin area without a frame does. The helper sits beside `SassStylesheet` in the tests' shared
library and reads a sheet the way Puls's `SiteColoursTests` does. The script is the one every site already
loads. No new package.

## Steps

Each step is one commit with its test, written first and seen failing on an assertion. Stop after each for
Louis's review. A step that meets a choice this plan does not settle stops and puts it to him.

### Step 1: the plan is kept

![The two plans, their pictures, the two designs and the three records go in together](diagrams/F151.1-the-theme-contract-step-1-the-plan-is-kept.svg)

A docs-only step, so it has no test first. It commits the parent's plan and this one, their pictures as JSON and
SVG together, the two designs in `plans/F151-mockups/`, and the records that go with a plan: the F151 row in the
TODO now lists the eight children and their done-whens, the plans' index has a row for each of the two plans,
and the work log's open table follows the TODO. ADR 0124, which Louis said yes to, goes in with them: the file,
its row in the ADRs' index and its line in the design rules.

It is checked by `dotnet test src/tests/tools/louis-agent.doc-diagrams.tests`, which holds every picture to its
JSON, and by the tests that hold the records, `WorkLogTests` among them.

### Step 2: a theme and a style are types

![Three small types: what a theme is, the two styles, and the names the browser side shares](diagrams/F151.1-the-theme-contract-step-2-a-theme-and-a-style-are-types.svg)

The tests come first. `SiteThemeTests` says a theme keeps its id and its name, and that an id is refused when it
is empty or holds anything but lower-case letters, digits and hyphens, with a message that names the id.
`SiteStyleTests` says the two styles are read from `light` and `dark` and written back the same, that any other
word is not a style, and that `SiteLook.DefaultStyle` is light.

Then the code. `SiteTheme` is a record of `Id` and `Name` that checks its id when it is made. `SiteStyle` is an
enum, `Light` and `Dark`. `SiteLook` is a static class with five things: `ThemeKey` is `site.theme`, `StyleKey` is
`site.style`, `ThemeAttribute` is `data-theme`, `StyleAttribute` is `data-style`, and `DefaultStyle`. The refusal's
words go in the message enum with a holes record, never inline.

Run `louis-agent.web.tests`, and `louis-agent.core.tests` since a folder is added.

### Step 3: an area may be a theme

![The slot: an area carries a theme or none, and the areas give the themes back in the order named](diagrams/F151.1-the-theme-contract-step-3-an-area-may-be-a-theme.svg)

The tests come first, as new cases in `SiteAreasTests`. With two areas that each carry a theme and one that
carries none, `Themes` holds the two in the order the areas were named and `DefaultTheme` is the first. With no
theme named, `Themes` is empty and `DefaultTheme` is null. An area named twice still counts once, so its theme
is listed once.

Then the code. `SiteArea` gains one optional last parameter, `SiteTheme? Theme = null`, so every area written
today still compiles. `SiteAreas` gains `Themes` and `DefaultTheme`, built as `AdminCards` is. `SiteAreasBuilder`
does not change.

Run `louis-agent.web.tests`, and the accounts' and evals' tests since they build areas.

### Step 4: a theme is held to the names

![A helper reads a stylesheet and says which names a theme leaves unset, in which style](diagrams/F151.1-the-theme-contract-step-4-a-theme-is-held-to-the-names.svg)

This step builds the tool that F151.2 points at each real theme. It is a helper for tests, in the tests' shared
library.

The tests come first, in `ThemeSheetTests`, over stylesheets written in the test as text. Given the framework's
`:root` block, `NamesToSet` gives every name it sets. Given a made-up theme that sets every name in both styles,
`Missing` gives nothing. Given one that leaves a name out of its dark block, `Missing` for dark gives that name
and `Missing` for light gives nothing. Given a sheet with no block for the theme at all, `Missing` gives every
name.

Then the code. `ThemeSheet.NamesToSet(frameworkCss)` reads the names out of the framework's `:root` block.
`ThemeSheet.Missing(css, theme, style, names)` finds the block whose selector is
`:root[data-theme="{id}"][data-style="{style}"]`, with the id and the style's written form, and gives back the
names that block does not set.

Run `louis-agent.web.tests`.

### Step 5: the surfaces get names

![The new names a theme sets beside the colours, each with today's look as its value](diagrams/F151.1-the-theme-contract-step-5-the-surfaces-get-names.svg)

The colour names cannot say "glass", so this step adds the surface names the parent lists under *The names a
theme sets*, in a new sheet, `settings/_surfaces.scss`. Each takes today's look as its value, so no page changes.
A pane's fill is the panel colour, its edge is the hairline the shared frame draws, its corner is the frame's,
and its rim, light, shadow and blur are none. A bar's fill, edge and blur are what `SiteShell`'s header has
today. A press takes the framework's call-to-action fill and the ink that goes on it. The mark's three take what
`Orb.razor.scss` draws today, so read it first. A visitor's colour is the brightest text and the agent's is the
framework's purple, and the five violet steps all start as that one purple.

The test comes first. `SurfaceNamesTests` reads the sheet and holds it to the list of names, one for one, so the
contract cannot drift without a test saying so. It also holds that each site's `app.scss` forwards the surfaces
straight after the colours.

Then the sheet, and one line in each site's `app.scss`: louis-agent.dev's, code-review's, Puls's and the
starter's, which is also the template a new site is made from.

Puls's `SiteColoursTests` makes Puls set every name the framework sets, and reads the first blocks of Puls's
stylesheet to do it. Read that test before adding the sheet. If it asks for the new names, Puls gets a value for
each in this step, and if a new block upsets how it finds the two it reads, that is put to Louis, not worked
round.

Run `louis-agent.web.tests`, the site's tests, and code-review's, Puls's and the starter's, since each reads the
shared sheets.

### Step 6: the browser applies what it remembers

![Before the first paint the script sets the two attributes from what the browser kept](diagrams/F151.1-the-theme-contract-step-6-the-browser-applies-what-it-remembers.svg)

The test comes first. `FirstPaintLookTests` reads `first-paint.js` and holds four things: it reads the two keys
`SiteLook` names, it writes the two attributes `SiteLook` names, it sets a style only when the remembered word is
`light` or `dark`, and it sets a theme only when the remembered word is made of lower-case letters, digits and
hyphens. The keys and attributes are read from `SiteLook` in the test, so the two sides cannot disagree.

Then the script. Inside the `try` it already has, it reads the two words and sets `data-theme` and `data-style`
on the page's root element when each passes its check. When nothing is remembered it touches nothing, so the
page keeps what its file wrote.

Run `louis-agent.web.tests`.

### Step 7: every site says its default

![A rule test holds each site's index.html to the default its areas give](diagrams/F151.1-the-theme-contract-step-7-every-site-says-its-default.svg)

The test comes first. `SitesSayTheirLookTests` stands beside `SitesNameTheirAreasTests` and reads each site the
same way. It holds that a site's `index.html` writes `data-style` with the default style on its `<html>`, and
that it writes `data-theme` with the id of the site's default theme when the site names one and writes none when
it names none. No site names a theme yet, so today it holds the style alone. In F151.2 louis-agent.dev names
glass first, and this test then asks for it.

Then the files: `data-style="light"` on the `<html>` of louis-agent.dev's `index.html`, code-review's, Puls's and
the starter's, which is also the template's. Puls's `<html>` also says `data-bs-theme="dark"`, which is Bootstrap's own
and is left as it is.

Nothing in the stylesheets reads `data-style` yet, so no page changes.

Run `louis-agent.web.tests` and each site's tests.

### Step 8: the docs, and the pull request

![The design doc and the write-up, then main merged in and the full unit suite, then one pull request](diagrams/F151.1-the-theme-contract-step-8-the-docs-and-the-pull-request.svg)

The framework web's design doc, `projects/louis-agent.web.md`, gains a part on themes and styles: what each is,
how a site names a theme, the names a theme sets, and how the page says which is on, with the pictures a project
doc of its kind must show redrawn where they changed. The write-up goes in `learning/20-extensibility.md`, and
its row in the write-ups' list. This plan stays until F151 is done, since the parent's children table links to
it.

Then `main` is merged into the branch, the whole solution is built, and the full suite of unit tests passes.
Louis is asked for the push, and the pull request is opened.

## Verification

The tests named in each step, then the full unit suite once `main` is merged in. By eye: louis-agent.dev on this
PC looks as it does on `main`, on the landing, a demo and the admin, since this child changes no look. One thing
is checked by hand in the browser's own tools: with `site.style` set to `dark` in the browser's storage, a
reload shows `data-style="dark"` on the `<html>` element, and with it removed the element says `light`. No run
that spends money.

## Concepts

Step 3 is the one to study: a plug-in point added as one optional slot, so every existing area keeps working and
a library joins by adding to a list. That is extensibility, skill 20 in [the goal](../GOAL.md). Steps 4 and 5
are testing and shipping, skill 18: a contract written down as a list of names, and a test that pins the list so
it cannot change quietly.

## Not known yet

Whether Bootstrap's own `data-bs-theme` should follow the style is not settled here. louis-agent.dev's page does
not set it today and Puls's sets it to dark. F151.4 looks at whether any Bootstrap part we use needs it. How
Puls's colour test finds its blocks is read in step 5, and what that step does about it depends on what is
found.

## Approved during the build

**Step 5, how Puls's colour test finds its blocks** (Louis, 2026-11-15, his pick "a" of three). Puls's
`SiteColoursTests` took the first two `:root` blocks of its CSS as the framework's colours and Puls's own, and the
surfaces' block, forwarded straight after the colours, would have been the second. The surfaces stay a sheet of
their own, forwarded straight after the colours as step 5 says, and the test finds its blocks from `app.scss`'s
list instead: as many blocks as the framework's settings sheets listed before Puls's own are the framework's, and
the next is Puls's. Puls still sets every colour name. The surface names are not asked of it, since each one's
value is a colour name and so follows Puls's colours; F151.5 sets any Puls wants on top. Chosen over the surface
names inside the colours' own block, which would have made Puls copy twenty-three values, and over forwarding
the surfaces after a site's own sheets, which would let the framework's defaults win over a site's.

**Step 5, where the theme tests sit** (Louis, 2026-11-15, his pick "A" of three). With `SurfaceNamesTests`,
`Rules/Styles/` in the web's tests held seven source files, one over the folder rule. `ThemeSheetTests` and
`SurfaceNamesTests` move into `Rules/Styles/Themes/`, namespace `LouisAgent.Web.Tests.Rules.Styles.Themes`, in place
of the folder the namespace map names for them. Chosen over moving the scoped-style tests into a folder of their
own, which would move files F151 has no part in and leave the folder full, and over a colours folder taking four
files, two of them not F151's.

**Step 7, who holds the theme a page writes** (Louis, 2026-11-15, his pick "A" of three). The framework's tests
read a site's program as text and cannot call its areas, so they cannot know its default theme without naming the
theme packages. The check is split. `SitesSayTheirLookTests` in the web's tests holds the style half for every
site found on disk. A shared check in the tests' library, `IndexLook` in `louis-agent.web.testing/Sites/`, with
`SiteProject` beside it to find a site's folder, compares what a site's `index.html` writes with what its own
areas give: their default theme, or none, and light. Each site's own test project calls it with its areas, in an
`IndexLookTests` of its own. Chosen over the style half alone, which would leave the theme a page writes unchecked
on three sites, and over the framework's test reading a program's text for the theme packages' calls, which would
have the framework name them.
