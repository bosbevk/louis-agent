# F171.1 A photo or a PDF reaches a tool

A plan: how the engine comes to take a photo or a PDF and keep it with the session, and how a pack's tool, given a
model in its constructor, has that model read the file into a record. It is the first of the eight children of
[F171 The bill checker](F171-the-bill-checker.md), which says what was decided and why. This file says what this
child builds, then gives its ten steps.

![Four parts: the API takes a file as bytes, the session keeps it, the program's catalogue hands each pack the model it picks, and the tool has that model read the file into its record, with the cost in the ledger](diagrams/F171.1-a-photo-or-a-pdf-reaches-a-tool-overview.svg)

## Context

Louis, 2026-11-22: "this feature is next", and then "nxt" for its first child. The bill checker reads a municipal
account from a photo or a PDF. Today the engine can't take either. This child is the framework's half of that:
nothing in it knows what a bill is. Louis, 2026-11-22: "the engine should be generic ain't it, it should not
contain rules from packs". The bills pack that uses it is F171.2, in the product's own repository.

**Why this plan was rewritten.** The first version, merged on 2026-11-22, had the engine offer a reader on the pack
context. The next day Louis set a rule for every tool instead: "tools as an architecture say someone just want to
use my tool, we must make our tools either take a model or our interface". He picked Microsoft's `IChatClient`,
and ADR 0028 now says a tool that needs a model takes `IChatClient` in its constructor, never a provider of ours,
and that no pack references `LouisAgent.Core` or a provider (PR #549, held by `PackConvertibilityTests`). On
2026-11-23 he tapped "Change F171.1 to IChatClient", and this plan replaces the first. Nothing of it had been built
beyond the plan itself.

**What the code has today.** A message to the API may carry attachments, and an attachment is a name and a text
(`AttachmentRequest(string Name, string? Content)`). The API pastes each one into the prompt, cut at 100,000
characters, and the session keeps them by name so an asked agent can be handed one later (`SessionAttachments`).
A user's turn reaches the model as one string. A pack builds its tools from the pack context, which holds the
workspace, the web and the site's places, and no model. A program builds its catalogue before the host starts
(`AgentHost.Build(SiteCatalog.Create(), services)`), and the host makes the model only after that. Two side jobs
already call a model outside the conversation, the summary of an oversized tool result and an eval's judge, and
each runs under its own purpose in the usage ledger. The summaries' client is the instance's model wrapped in
core for traces, the eval replay and the ledger (`ChatPipeline.BuildSummaryClient`). Nothing in the repository
sends an image or a document to a model, and nothing asks for an answer in a schema.

**What was read on 2026-11-22**, each at its source. Microsoft.Extensions.AI gives a file to a model as
`DataContent`, bytes with a media type, and `GetResponseAsync<T>` asks for an answer that fits the JSON schema of
`T` and gives it back as a `T` ([the library's docs](https://learn.microsoft.com/dotnet/ai/ichatclient)). Claude
reads JPEG, PNG, GIF and WebP images of up to 10 MB each, and PDFs. A PDF's pages each go in as text and as an
image, at about 1,500 to 3,000 tokens a page, and "All active models support PDF processing". A request to the
Messages API may weigh 128 MB ([PDF support](https://platform.claude.com/docs/en/build-with-claude/pdf-support),
[the API's overview](https://platform.claude.com/docs/en/api/overview)). Structured output takes no limits on a
number's size or a string's length in the schema. Haiku 5.5 costs $0.10 for a million tokens in and $0.50 out, and
Sonnet 5.5 $2 and $10 ([pricing](https://platform.claude.com/docs/en/about-claude/pricing)), so a reading of a
photo costs roughly a tenth of a US cent on Haiku and two cents on Sonnet. MCP deprecated sampling, the way a
server asked its client's model for an answer: "Servers that need LLM capabilities can integrate directly with LLM
provider APIs" (SEP-2577).

**What was read on 2026-11-23**, for how a tool gets its model. Microsoft's DI guidelines, updated 2026-03-11:
"Avoid using the service locator pattern", and "Another service locator variation to avoid is injecting a factory
that resolves dependencies at runtime" ([the guidelines](https://learn.microsoft.com/en-us/dotnet/core/extensions/dependency-injection-guidelines)).
Fowler: "Constructors with parameters give you a clear statement of what it means to create a valid object in an
obvious place" ([Inversion of Control Containers and the Dependency Injection pattern](https://martinfowler.com/articles/injection.html)).
Microsoft registers a model with a factory at the composition root, `AddChatClient(services => ...)`
([IChatClient](https://learn.microsoft.com/en-us/dotnet/ai/ichatclient)). A function can also be handed services
per call through `AIFunctionArguments.Services`
([Access data in AI functions](https://learn.microsoft.com/en-us/dotNET/ai/how-to/access-data-in-functions)),
which is the locator the guidelines warn of.

**What could not be confirmed.** The Anthropic package we use (12.53.0) holds the words for PDFs, the four image
types and a JSON schema, so its adapter looks able to send a file and ask for a schema. No run has shown it. Haiku
5.5's own page says it takes "Text and images", and says nothing of PDFs, of structured output or of the
high-resolution tier the parent plan names for it. Step 2 proves all of this with two live readings, and the plan
stops there if they fail.

**What Louis picked for this child.** On 2026-11-23, three cards. How the tool's constructor gets its model: "B: the
catalogue injects it", the program's catalogue hands the model to the pack's constructor, over the pack context
handing one out and over a function's services per call. On the way he asked "can we not pass our own engine?",
and that is what our hosts do: the client a tool gets is the engine's own model, already wrapped. How the
catalogue gets that wrapped model, since it is built before the model exists: "1: host calls the catalogue", the
host makes the models and then calls the program's catalogue function with them, over a stand-in filled later and
over each program building its own. Which model a pack gets: "3: a model per pack in code", the catalogue picks one
for each pack by its profile's name, over one setting for every tool and over keeping `READER_LLM`. So this child
has no `READER_LLM`, and no reader in the engine. What he picked on 2026-11-22 and still holds: the engine stays
generic, and every reading has its own row in the ledger with its cost.

## Design

### 1. What a tool gets, and from where

A tool that reads a file needs two things: a model, and the file. They come from two places, because they live for
different lengths of time.

The model lives as long as the host. So the tool takes it in its constructor, as ADR 0028 now says, and the pack
that builds the tool takes it in its own. The program's catalogue is where packs are made, so that is where the
model is handed over: `new BillsPack(models.Named("haiku"))`. The catalogue picks the model for each pack, in
code. The tool itself sees only Microsoft's `IChatClient`, so someone outside our framework writes
`new ReadSampleTools(theirClient, theirFiles)` and it works the same.

The file lives as long as one session, and the pack is built once for the whole host. So the file can't go in a
constructor. It comes from the pack context, where a tool already finds the browser or the site's places: the tool
gives a name and gets the file, its type and its bytes. That is the one new member on the pack context, and it
holds nothing of Microsoft.Extensions.AI, so `LouisAgent.Composition` stays as small as it is.

The interface picture is in two halves, the model and then the files, since in one it was too wide to read.

![AgentHost creates ToolModels, whose wrapped clients implement IChatClient, and uses the program's catalogue, which creates the pack, which creates its tool with the model it picked](diagrams/F171.1-a-photo-or-a-pdf-reaches-a-tool-interface-design-the-model.svg)

![The pack context gains Files; TurnSessionFiles and NoSessionFiles implement it; the pack hands context.Files to its tool beside the model](diagrams/F171.1-a-photo-or-a-pdf-reaches-a-tool-interface-design-the-files.svg)

```csharp
// LouisAgent.Composition: what a pack may ask about the session's files.
public interface ISessionFiles
{
    SessionFile? Find(string name);
    void Forget(string name);
}

public sealed record SessionFile(string Name, FileMediaType MediaType, ReadOnlyMemory<byte> Bytes);

// LouisAgent.Core: what the host hands the program's catalogue.
public sealed class ToolModels
{
    public IChatClient Instance { get; }
    public IChatClient Named(string profile);
}

// A program's start, when one of its packs needs a model.
var host = AgentHost.Build(models => SiteCatalog.Create(models), services);
```

`Named` takes a profile from `LLM_SESSION_PROFILES` and throws `SessionLlmException` with the names it has for one
that isn't there, so a typo stops the host at start-up and never at a visitor's first upload. That is the same
message a session gets today when it names a profile the instance doesn't offer.

The host builds `ToolModels` once, before it calls the catalogue function. Each client in it is wrapped the way the
summaries' client is: traced, answered from the eval's recordings when a trial replays, and written to the ledger,
with the profile's own usage mapping. One more layer opens a usage scope whose purpose is `tool` around each
request, so the ledger tells a tool's call apart from a turn, a summary or a grading, and keeps the turn's host,
session and turn. That is the whole of what the engine adds for a model: it knows nothing of reading, files or
records. The pack brings its instructions and its record type, and does the reading itself.

A pack that needs a model can't be served by our MCP tool host, which has no model at all and is built with an
`AgentCatalog` as today. The catalogue function is only on `AgentHost.Build`, the path the API takes and the bills
checker's program will use. The CLI, the ACP server and the MCP host gain it when a program of theirs needs it.

### 2. How a tool reads a file

There is no reader class. The tool does what Microsoft's library already does in one call: it builds a user message
holding its instructions as text and the file as `DataContent` with the file's media type, and asks
`GetResponseAsync<T>` for its record. A failure from the provider, an empty answer or one that doesn't fit the
schema is caught by the tool and turned into text with the reason, as every pack's tool returns a failure today
(ADR 0005). The made-up tool in the tests, `ReadSample`, shows the shape in about ten lines, and the guide for a
pack author shows it at the close. A second pack that reads files would repeat those ten lines, and a shared piece
waits until one does (ADR 0055).

### 3. Where each part goes

![The wire carries the bytes, the API keeps them, the contracts say what a pack may ask about files, core wraps the models and calls the catalogue, and the pack's tool calls the model](diagrams/F171.1-a-photo-or-a-pdf-reaches-a-tool-architecture.svg)

The bytes travel inside the message's JSON as base64, the way the admin's price import already sends a file
(`ImportFileBody`, with its content as a `byte[]`), so the API needs no form and no second endpoint. An attachment
that carries bytes is a file, and one that carries text is what it is today.

The API checks a file before it keeps it. Its type must be one of the five the enum names, and it may weigh at
most 10 MB, which is Claude's own limit for an image. A session keeps at most 20 MB of files, the import's number.
A file that fails a check is refused with a 400 that says which check. The bytes live in memory with the session,
as its history does, and are never written to a log or to disk.

The model that runs the conversation never gets the bytes. It reads one line that says a file is attached, with
its name, type and size, and a tool can then be given that name. That keeps the conversation small and keeps the
photo out of every later request of the chat.

### 4. The main case

![The program's catalogue gets the models at start-up; the photo travels as bytes and stays with the session; the conversation's model sees only its name; the tool makes one call on the model it was given and the ledger gets one row](diagrams/F171.1-a-photo-or-a-pdf-reaches-a-tool-communication-a-tool-reads-an-upload.svg)

At start-up the host makes `ToolModels` and calls the program's catalogue function, which builds the made-up pack
with `models.Named("haiku")`. Later a caller sends "check this" with `account.jpg` as bytes. The API checks it and
keeps it with the session, and the conversation's model reads only the line that names it. The model asks the tool
for `account.jpg`. The tool finds the file through the pack context, sends its instructions and the bytes to the
model it was given, gets its record back, and returns it as text. The wrapped model wrote one ledger row on the
way, purpose `tool`, with its cost.

The host builds one pack context for all its sessions, so the context can't hold one session's files. It reaches
them the way an asked agent reaches the session's text attachments today: the API sets them for the turn, and the
context reads what is set (`SessionAttachments` is the code to copy).

![The host holds ToolModels and the one pack context; the pack holds its model; one session holds the conversation as text and the upload as bytes, reached for this turn through the flow](diagrams/F171.1-a-photo-or-a-pdf-reaches-a-tool-objects-in-memory.svg)

### 7. What is reused

No new package. A pack that needs a model references `Microsoft.Extensions.AI.Abstractions` itself, as ADR 0028
says, and `LouisAgent.Composition` doesn't change its references. `DataContent` and `GetResponseAsync<T>` come with
Microsoft.Extensions.AI, which the engine is built on (ADR 0002). The tool models are stacked as the summaries'
client is, traced, replayed and recorded by `UsageRecordingChatClient`; the one new layer only opens a
`UsageScope`. `Named` reuses the profiles `SessionLlmLoader` already loads and the message a session gets for an
unknown one. The turn's files copy `SessionAttachments`. The bytes in JSON copy the import. `NoSessionFiles` copies
`NoSitePlaces`. The media type is an enum read once with `SettingChoice.TryParse` and written with `.Wire()`
(ADR 0024). The refusals and the line the model reads are message enums with holes records (ADR 0009).

### 8. What this child leaves out

The web chat's composer still attaches text only, since the phone app's own composer is F171.6's. A file is not
handed on to an agent asked on another instance. Nothing is stored past the session: keeping a bill with an
account is F171.5's. The Files API, which would upload a file once and name it in later requests, is not used,
because one reading sends a file once. The CLI, the ACP server and the MCP host keep taking an `AgentCatalog`, and
our MCP tool host serves no pack that needs a model.

## Steps

Each step is one commit with its test, written first and seen failing on an assertion. Stop after each for
Louis's review. A step that meets a choice this plan does not settle stops and puts it to him.

### Step 1: the plan is kept

A docs-only step, so it has no test first. It commits this plan and its six pictures, as JSON and SVG together,
in place of the first version, its row in the plans' index, and a line under the parent's *Approved during the
build*. If Louis says yes to the new line for ADR 0028 (under *Verification*), it goes in here.

Checked by `dotnet test src/tests/tools/LouisAgent.DocDiagrams.Tests` and the Docs tests in `LouisAgent.Core.Tests`.

### Step 2: the adapter is proved

This step proves what the rest stands on, before anything is built on it. The test is live and costs well under
a US cent: it builds the Anthropic client as a host does, sends a made-up account as a JPEG and then as a PDF
with a small record's schema through `GetResponseAsync<T>`, and asserts the record comes back with the account
number and the amount on the page. It is marked as an integration test and skips, saying so, where no key is set.
The two sample files are drawn for the test and show no real person or account.

There is no code to write after it, so this is the one step whose test is not seen failing first. If either
reading fails, the plan stops here and the ways on go to Louis as a finding: Haiku 5.5 may need another model for
PDFs, or the adapter may need the provider's own client behind a strategy (ADR 0003).

Run the one test with a key, and report what it cost.

### Step 3: an attachment carries bytes

The test comes first, as new cases in `SessionRequestJsonTests`: a message whose attachment has bytes and a media
type is read from JSON with its bytes whole, and written back the same, and a message with a text attachment
reads exactly as it does today.

Then the code. `AttachmentRequest` gains two optional last members, `byte[]? Bytes = null` and
`string? MediaType = null`, so every caller written today still compiles.

Run `LouisAgent.SessionStream.Tests`, and the API's tests since they send messages.

### Step 4: what a pack may ask about files

The tests come first, in `PackContextFilesTests`. A pack context that says nothing of files finds none and forgets
without complaint. `FileMediaType` reads `image/jpeg`, `image/png`, `image/gif`, `image/webp` and
`application/pdf`, writes each back the same, and takes no other word.

Then the code: the four types of the map's step 4, and `Files` on `IPackContext` with a default, as `Places` has
one.

Run `LouisAgent.Core.Tests`, since a folder is added and the rule tests read it, and
`LouisAgent.Packs.Rules.Tests`, since `PackConvertibilityTests` holds the packs' shapes.

### Step 5: the session keeps a file

The tests come first, in `SessionFilesKeptTests`. A message with a JPEG of 1 MB is accepted and the session then
holds a file of that name, type and size. The same name again replaces it. A type that is not one of the five is
refused with a 400 that names the type. A file over 10 MB is refused with a 400 that names the limit, and so is
one that would take the session past 20 MB. A text attachment is kept as it is today.

Then the code. `AgentSession` keeps `SessionFile`s by name beside its text attachments, with the two limits as
named constants. `SessionHandlers.SendMessage` checks each attachment that carries bytes before the turn starts.
The refusals' words go in `ApiUserText`.

Before the code, read what the API allows a request to weigh. Nothing in the repository sets it, and a 10 MB file
is about 13.4 MB as base64. If the server's own limit is under that, it is put to Louis.

Run `LouisAgent.Api.Tests`.

### Step 6: a tool finds this turn's files, and the model is told the name

The tests come first. In core, inside a turn whose host set two files, the pack context finds each by name,
whatever the case of its letters, finds nothing for a name that isn't there, and no longer finds one it was told
to forget. Outside a turn it finds none. In the API, the prompt for a message with a file holds one line with the
file's name, type and size, and holds none of its bytes.

Then the code. `SessionFiles` holds the turn's files for the flow, as `SessionAttachments` holds the text ones.
`TurnAmbience` sets it. `TurnSessionFiles` is what `ToolsetContext.Files` gives. `TurnPrompt` writes the line from
`ApiModelText.AttachedFile`.

Run `LouisAgent.Core.Tests` and `LouisAgent.Api.Tests`. The line is new text the model reads, so regenerate the
golden files it touches.

### Step 7: the models a tool may be given, wrapped once

The tests come first, in `ToolModelsTests`, over model clients made for the test. A request through `Instance`
reaches the instance's client. Inside a turn's usage scope, its ledger row has the purpose `tool` and keeps the
turn's host, session and turn. A request through `Named("haiku")` reaches that profile's client, and its row names
that profile's model. A name that isn't a profile throws `SessionLlmException` with the names there are.

Then the code. `UsagePurpose.Tool` beside `Summary` and `Grading`. `UsagePurposeChatClient` opens the scope around
each request, streamed or not. `ChatPipeline.BuildToolClient` stacks it over the summaries' layers. `ToolModels`
builds one such client for the instance and one for each profile, with the profile's own usage mapping. Its
summary names the picks: the catalogue hands each pack its model, chosen over the pack context and over a
function's services, and picks it per pack in code, chosen over one setting (Louis, 2026-11-23).

Run `LouisAgent.Core.Tests`.

### Step 8: the program's catalogue gets the models

The tests come first, in `AgentHostCatalogueTests`, on a host built from a client factory made for the test, as
the ledger's tests build one. The catalogue function is called once, with models whose `Instance` is the wrapped
instance model. Its made-up `ReadSamplePack`, given `models.Instance`, is in the engine's toolsets. Its tool, asked
for a file the turn holds, sends the fake provider one request that holds the instructions, the file as
`DataContent` with its media type, and a response format that is `SampleAccount`'s schema, and returns the record
as text. The ledger has one `tool` row. A provider that fails makes the tool return text with the reason, never an
exception, and a cancelled call stays a cancellation.

Then the code. `AgentHost.Build` gains the overload that takes `Func<ToolModels, AgentCatalog>`. It opens the
ledger and the eval's store of recordings first, builds `ToolModels` on them, calls the function, and goes on as
today with the catalogue it gets back. `AgentEngineFactory` is given that one store, so the engines and the tool
models replay from the same recordings. The overload that takes an `AgentCatalog` stays, and every program that
uses it today is left as it is.

Run `LouisAgent.Core.Tests`.

### Step 9: a reading replays

An eval replays a recorded run without paying for it, so a tool's model call must be found again by what was
asked. The test comes first, in `ToolModelReplayTests`: a reading recorded once is answered from the recording the
second time, and the same instructions with one byte of the file changed is a miss.

A recording's key hashes each message's contents and the request's options, the response format among them, so
this may pass as written. If it does, the commit is the test alone, and says so. If the key leaves the bytes or
the schema out, the fix is here.

Run `LouisAgent.Core.Tests`.

### Step 10: the whole path, and the close

The test comes first, live, in the API's integration tests: a host whose catalogue function builds a made-up pack
on `models.Instance` is sent the sample JPEG, then the sample PDF, and each time the answer holds the account
number from the page and the ledger has a `tool` row with a cost. It skips, saying so, without a key.

Then the close, with `/finish-a-feature`: the design docs of the projects this child touched
(`LouisAgent.Core`, `LouisAgent.Api`, `LouisAgent.Composition`) and their pictures, a part in the guide for a pack
author on a tool that reads a file, the skill map's row 19, the write-up, the records, and this plan deleted.

## Verification

Every step's tests are named in it. Before the pull request, `main` is merged in and the full suite runs in the
pull request's checks, with Core's rule tests run here first. The live readings are four in all, in steps 2 and
10, each well under a US cent on Haiku 5.5. They are test calls, so they run without asking and their cost is
reported after.

**Done when:** a test sends a JPEG and a PDF through the real adapter and gets a typed record back, and a usage
row has the reading's cost. That is the parent's done-when for this child.

**For Louis's yes: one new line in ADR 0028.** The ADR says what a tool takes, and later packs must also know how
our hosts hand it. Proposed, under the line #549 added: "Our hosts hand that model through the program's
catalogue: `AgentHost.Build` calls the catalogue's function with the instance's models, each already traced,
replayed and written to the ledger, and the catalogue picks one for each pack by its profile's name. No pack
context carries a model."

**After the merge.** The bills pack takes this from the framework's packages, so a new version of
`LouisAgent.Composition`, `LouisAgent.SessionStream`, `LouisAgent.Core` and `LouisAgent.Api` has to be tagged
(ADR 0130). The tags are Louis's to say.
