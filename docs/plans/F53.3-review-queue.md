# F53.3 The review queue

> **Plan.** The third child of [F53](F53-admin-by-job.md): grading what waits for a person, as one job on one page,
> instead of a hunt through the runs. Built unattended (Louis, 2026-11-03: "implement this unattended, PR and
> merge"), so each finding below takes the recommended option and says so; Louis can reverse any in the review.

Status: **approved 2026-11-03** (part of F53's approval).

## Context

A human review (`meal-for-people.human`) is a grader the runner leaves *pending* on every conversation; a person
answers it in the run page's explorer (`ReviewPanel`, F18 step 6a.3), one conversation at a time, about seven
clicks from the portal's door, once per run. Nothing says how many answers wait. The run page's verdict (F53.1)
counts them per run; this plan gives them one page across runs, with the keys 1, 2 and 3 and a count in the sidebar.

GOAL skills: **16 Human in the loop** (people grading answers, now as a queue) and **12 Evaluation**.

## Findings, each with the recommended option taken

### A. Whose queue is it?

The explorer's rule (`ReviewStatus`, 6a.4d, Louis: "I need to know which ones to check") is per reviewer: a pending
review this reviewer hasn't answered is *to review*, one they have is *reviewed*, whatever its case.

1. **The queue is this reviewer's** (taken): `GET …/reviews/queue?reviewer=Louis` lists the answers Louis hasn't
   graded; without a name, the answers nobody has. The same rule as the explorer, in the API. Costs: a name before
   the count means anything; the sidebar shows "nobody's" count until one is kept.
2. Everyone's queue: an answer leaves once anyone grades it. Simpler, but a second reviewer never sees what the first
   did, and the calibration wants more than one person's labels.
3. A queue per judge: pick the judge first. More to click for one judge today.

### B. Where the reading happens

1. **The API answers the whole item** (taken): the run, the eval, the conversation's row with its grades and the
   people's grades, the questions asked and the last answer, as the contract's rows. The page reads one route, and
   `ReviewPanel` takes the item as it takes a conversation in the explorer. Costs: the API fetches turns per item,
   so the route takes a `limit` (20) and says the total.
2. The API lists keys only and the page fetches each run: one route per run opened, the page does the joining.
3. The page reads every run itself: no API change, but the list of runs is capped at 50 and the page would read each.

### C. The keys

1. **1, 2, 3 on the page, the panel's own buttons stay** (taken): the page listens on its own container and calls
   the panel's grade; the panel reports a grade given, and the page opens the next item. Costs: `ReviewPanel` gets a
   public `GradeAsync` and an `OnGraded` callback.
2. Keys inside the panel: every panel in the explorer would answer keys too, where they would surprise.

### D. The count in the sidebar

1. **A scoped state the badge and the page share** (taken): `ReviewQueueState` holds the count and raises `Changed`;
   the badge reads the queue once when the layout opens (with the kept name) and the Review page sets the count as it
   loads and after each grade. The pattern `ReviewerState` and `CurrencyState` use. Costs: one more read on open.
2. The badge polls like the live-run strip: more reads for a number that changes only when this person grades.

## Design

**API** (`src/louis-agent.api`): `ReviewQueries.QueueAsync(store, reviews, reviewer, take)` walks the newest runs
(`ListRunsAsync`, 50), keeps a run with human reviews, and for each conversation with a pending review grade this
reviewer hasn't answered (none without a name) yields the item, fetching its turns only for the first `take`.
`ReviewQueueHandlers.GetQueue` answers `ReviewQueueReply(Items, Total)` where an item is
`ReviewQueueItem(Run, Eval, StartedAt, Graders, Conversation, Asked, Answer)` (`RunGraderRow`, `ConversationRow`,
the contracts the run page already reads). Route `GET /v1/admin/evals/reviews/queue?reviewer=&limit=`, under the
same prefixes as the run's reviews.

**Portal** (`src/louis-agent.puls`): `Pages/Admin/Review.razor` at `/admin/review` reads the queue with the kept
name and shows one item: where it is from (eval, run, mode, task, a link to the run), then `ReviewPanel` with the
item's rows; a side list says done and left; *Skip* moves on without a grade; a grade given opens the next.
`ReviewQueueView` (a Presentation Model) holds the items, the open index, done and left. `ReviewQueueState` (scoped)
holds the count; `ReviewCountBadge` in the sidebar shows it beside *Review*.

## Concepts

**An annotation queue** (GOAL skill 16): a reviewer's job as a queue with a done count, keyboard shortcuts and
"next opens by itself", the shape every labelling tool takes (Label Studio, Prodigy). **Blind by construction**: the
queue item carries the judge's grade, but the panel draws it only after the person's own (F18's rule, unchanged).
