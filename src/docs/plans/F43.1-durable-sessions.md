# F43.1 Durable sessions

A plan: how the API comes to keep each chat in a store behind one seam, so a restart no longer ends it, with an
in-memory store and a MongoDB one, MongoDB in the local compose and on Azure as a free DocumentDB cluster. It is the
first child of F43 *Accounts, tenants and durable sessions*. This file says what it builds, then gives its ten steps.

![F43.1 durable sessions: one seam with two stores, a session saved as its opening and then a turn at a time, resumed on its next message after a restart, kept 30 days idle, on MongoDB locally and Azure DocumentDB live](diagrams/F43.1-durable-sessions-overview.svg)

## Context

The TODO's order puts this next, after F171.1, among the rows that make the framework ready for production (Louis,
2026-11-22: "to get it ready production ready for apps to be built on it"). F43's row records why: an outside
comparison with Microsoft Agent Framework, LangGraph and OpenAI's Agents SDK found that losing every session on a
restart was the biggest gap, and his pick that day was a session store behind one seam, with an in-memory and a
MongoDB provider, and a session that resumes after a restart. Louis, 2026-11-25: "nxt".

What was looked up, on 2026-11-25:

- **How the three keep a session.** Microsoft Agent Framework serializes a thread to JSON and lets a custom
  `ChatMessageStore` keep the history under a key of its own
  ([persisted conversation](https://learn.microsoft.com/en-us/agent-framework/tutorials/agents/persisted-conversation),
  [agent memory](https://learn.microsoft.com/en-us/agent-framework/user-guide/agents/agent-memory)). LangGraph saves
  a checkpoint per step through one checkpointer seam: `InMemorySaver` for development, then SQLite, Postgres or
  `MongoDBSaver` ([persistence](https://docs.langchain.com/oss/python/langgraph/persistence)). OpenAI's Agents SDK has
  a `Session` protocol, SQLite by default and SQLAlchemy or Redis for production
  ([sessions](https://openai.github.io/openai-agents-python/sessions/)). All three: one seam, memory by default, a
  database for production.
- **Where MongoDB could run.** No database runs in the sites' Azure today, only a file share (`main.bicep`). Azure
  DocumentDB, the 2025 name of Cosmos DB for MongoDB vCore, has a free tier: a cluster with 32 GB, free for the
  account's life, no backup or restore
  ([free tier](https://learn.microsoft.com/is-is/azure/cosmos-db/mongodb/vcore/free-tier),
  [limits](https://learn.microsoft.com/en-us/azure/cosmos-db/mongodb/vcore/limits)); those pages date from 2023 and
  2024, so step 8 proves the tier with a `what-if` before anything relies on it. Its Bicep is Microsoft's verified
  module `avm/res/document-db/mongo-cluster`
  ([AVM index](https://azure.github.io/Azure-Verified-Modules/indexes/bicep/bicep-resource-modules/print.html)); its
  current version could not be read today, and step 8 pins it.
- **What the repo has.** The API references `MongoDB.Driver` 3.12.0 and no code of it uses it since Puls left, so no
  package is added. CI runs a throwaway `mongo:7.0` (`.github/workflows/ci.yml`), so the store's contract runs against
  a real MongoDB there. `AgentSessions` keeps sessions in a `ConcurrentDictionary` and drops one idle for four hours;
  a session is opened from a `SessionRequest` by `SessionOpening`. ADR 0048 says MongoDB goes through typed records,
  ADR 0008 that history is append-only and a finished turn is appended whole.

Louis's picks, 2026-11-25, on four cards: MongoDB **locally and on Azure DocumentDB** in this child; the store keeps
**the conversation only**, never a chat's photos or PDFs, which stay in memory as F171.1 built them; a
**`SESSION_RETENTION` setting, 30 days idle by default**; and a **session document plus one document per turn**.

## Design

### 1. One seam, two stores

`AgentSessions` keeps holding the sessions it is serving in memory, as today, and writes each one through
`ISessionStore`. The seam has four calls: save how a session opened, append a finished turn, load a session back,
and delete one. `InMemorySessionStore` keeps them in a dictionary, for tests and for a host that sets no database;
`MongoSessionStore` keeps them in two typed collections. A setting picks one when the host starts
(`SESSION_STORE`, `memory` or `mongo`), so neither the session nor its turn knows which. It is a Separated
Interface with a Strategy per store, the shape all three frameworks above chose.

![The interface design: AgentSessions uses ISessionStore, which the in-memory and the MongoDB store implement, holding a StoredSession and its StoredTurns; SessionOpening opens a session again from its stored request](diagrams/F43.1-durable-sessions-interface-design.svg)

### 2. What is saved, and when

When a session opens, the store gets a `StoredSession`: its id, the request it opened with, its text attachments,
its turn count and when it was last used. When a turn finishes, the store appends a `StoredTurn`: its number and the
messages the turn added to the history, written whole as Microsoft.Extensions.AI's own JSON, so a thinking block's
signature survives (ADR 0008), and the session's turn count and last activity move on. Nothing earlier is ever
rewritten, and no document nears MongoDB's 16 MB however long the chat runs. The system prompt is not saved: it is
built again from the prompts the host runs, as for any session.

What is not saved: a chat's photos and PDFs (F171.1 keeps them in memory, never on disk), the agents a chat keeps open
on a peer (a resumed chat opens them again when it asks), and an eval trial's session, which replays from its
recordings and has no next day.

### 3. Resumed on its next message

`AgentSessions.Get` becomes `GetAsync`. An id it holds is answered from memory as today. An id it doesn't hold is
read from the store; if the store has it, `SessionOpening` opens the session again from its stored request with the
same id, its history is restored from its turns after the system prompt, and its attachments and turn count come
back. The turn then runs as if nothing happened. An id the store doesn't have either is the 404 it is today.

![A chat across a restart: the session is saved as it opens and after each turn; after the restart the next message reads it back, opens it again with the same id and its history, and the turn goes on](diagrams/F43.1-durable-sessions-communication.svg)

### 4. How long it is kept

A session idle in memory for four hours is still dropped from memory, as today, but no longer lost: its next message
reads it back. The store keeps it for `SESSION_RETENTION` after its last activity, 30 days when unset, and MongoDB
deletes it then by a TTL index on that time, its turns with it. Deleting a session through the API deletes it from the
store at once. The privacy page says so.

![Objects in memory: one AgentSessions and one store per host; a session in memory holds its engine, history and files; the store holds its opening and a document per turn](diagrams/F43.1-durable-sessions-objects.svg)

### 5. Where MongoDB runs

Locally, a `mongo:7.0` container joins the site's compose, the version CI runs. On Azure, a free-tier DocumentDB
cluster joins `main.bicep` on Microsoft's verified module, every name a parameter (ADR 0131), and its connection string
is a secret `deploy.ps1` puts beside the admin key, which the site's app reads as `SESSION_STORE_URL`. A person deploys
it with `deploy.ps1 infra`, never CI. The framework site's host is unchanged in this child: it keeps the in-memory
store.

![The architecture: the site's API writes through the store a setting picks; MongoDB in the local compose, a free DocumentDB cluster on Azure, and the privacy page saying what is kept](diagrams/F43.1-durable-sessions-architecture.svg)

### 8. What is reused

No new package: `MongoDB.Driver` 3.12.0 is already the API's, and the Bicep module is Microsoft's verified one. The
documents follow ADR 0048 (typed collections, `[BsonElement]` names, dates as UTC). The messages are written with
`AIJsonUtilities.DefaultOptions`, as the model's replay recordings already write them, which keeps thinking blocks
whole. The setting is an enum read once with `SettingChoice` (ADR 0024), the URL a secret in `.env.secrets` and in
the vault as the admin key is. A session opens again through the same `SessionOpening` that opens a new one, so a
resumed session can't be built differently from a fresh one.

## Steps

Each step is one commit with its test, written first and seen failing on an assertion. Stop after each for Louis's
review. A step that meets a choice this plan does not settle stops and puts it to him.

### Step 1: the plan is kept

A docs-only step: this plan, its five pictures as JSON and SVG, its row in the plans' index, F43.1 in F43's TODO row
and the work log's open table. Checked by the Docs tests and `LouisAgent.DocDiagrams.Tests`.

### Step 2: the seam, and the store in memory

The tests come first, as a contract any store must keep: a saved opening loads back the same; turns append in order
and load in order; a load of an unknown id finds none; a delete removes the session and its turns. Then
`ISessionStore`, its two records and `InMemorySessionStore`. Run `LouisAgent.Api.Tests` and Core's rule tests.

### Step 3: a session is saved

The tests come first: opening a session saves its opening; a finished turn appends its messages, thinking included,
and the session's turn count; a deleted session is gone from the store; an eval trial's session is not saved; a
failed turn appends nothing it didn't add. Then `AgentSessions` and `TurnStream` write through the store, the
in-memory one by default. Run `LouisAgent.Api.Tests`.

### Step 4: a session resumes

The tests come first, as a restart: a second `AgentSessions` over the same store, given the first one's id, opens the
session again with the same toolsets, identity and role, and its next turn's request to the model carries the earlier
turns after the system prompt; an id neither holds is a 404. Then `GetAsync` and `SessionOpening` with a given id and a
restored history, and the routes that read a session. Run `LouisAgent.Api.Tests`.

### Step 5: the store in MongoDB

The contract of step 2 runs against `MongoSessionStore` on a real MongoDB, in the API's integration tests, asking for
it through `Outside` (skipped on a machine without one, required in CI), plus a test that the TTL index is on the last
activity with the retention given. Then the store, its two documents and its indexes. Run the integration project with
CI's `mongo:7.0` started locally.

### Step 6: the settings

The tests come first: `SESSION_STORE` reads `memory` or `mongo` and nothing else; `mongo` with no
`SESSION_STORE_URL` stops the host at start-up, saying so; `SESSION_RETENTION` reads a duration and is 30 days unset.
Then `SessionStoreOptions` and the host's wiring, a line each in SETUP and the site's `.env.example`. Run
`LouisAgent.Api.Tests`.

### Step 7: MongoDB in the local compose

A configuration step, no test first. `mongo:7.0` joins the site's compose with a volume, the site's API is set to
`mongo`, and the check is by hand: open a chat on :5080, restart the site container, send the next message, and the
agent still knows the chat. Its proof is written in the commit.

### Step 8: Azure DocumentDB

A configuration step. The free-tier cluster in `main.bicep` on the verified module, pinned; its connection string a
secret `deploy.ps1` writes from `.env.secrets`; the site's app yaml reads it as `SESSION_STORE_URL` with
`SESSION_STORE=mongo`. Checked by the Bicep check in CI and a `what-if` Louis runs against what runs. If the free tier
can't be had, the plan stops here and the ways on go to Louis. Louis deploys it with `deploy.ps1 infra`.

### Step 9: the privacy page says what is kept

The page's test changes first: "What you type" says the chat is kept for 30 days after its last message, then
deleted, and that photos and PDFs are never kept; Microsoft Azure joins the handlers as where it is kept. Then the
page, its words moved to a `PartWords` dictionary as ADR 0132 asks of a touched page. Run `LouisAgent.Site.Tests`, and
look at it on :5080.

### Step 10: the close

With `/finish-a-feature`: the API's design doc (a part on the store), SETUP, the session architecture spec's first
workstream marked as begun, the TODO's known limitation *Sessions are in memory* removed for the API, the write-up,
the records, and this plan deleted.
