# F126.3.3 The page a conversation names

A plan: how a run of an eval gives the agent the page its visitor is on. It is the third child of F126.3, *runs and
the run page*, in [F126 Evals, redesigned](F126-evals-redesigned.md), which says what was decided and why. This file
says what this child builds, then gives its eight steps. It adds no screen: starting a run from the admin is
F126.3.4's.

![Five parts: a page read on the server as a visitor's message carries it, a route that answers it, the run asking the route, the page kept with the run's recordings, and a live run that proves it](diagrams/F126.3.3-the-page-a-conversation-names-overview.svg)

## Context

**Why it matters.** On louis-agent.dev the guide sits in the corner of every page, and a visitor's first message
carries the page they are reading: its address, its title, its words, its named places, its links and its focus,
which is the part of the site the page is in. The guide answers from that, and it reads a part's own rules by the
focus. An eval that asks the guide the same question without the page tests a different agent than the one a
visitor meets. Anthropic's guide on evals says it plainly: "It's essential that the agent in the eval functions
roughly the same as the agent used in production."

**What the code has, on `main` at `3a83a07d`.** Three parts are already there. An eval file's conversation may name
a page, an address that starts with `/`, and the reader checks it. The wire's message request has a place for a page
(`PageRequest`), and the API turns one into a block of the prompt, cut at 6,000 characters. And a run says whether
it sent the page (`PageSent`), which is false in every run so far, since nothing sends one: the session client
sends a message's words and nothing else.

What builds the page today is the browser. The widget's own module reads it when a message is sent
(`ChatWidget.razor.js`): the visible text of the page's main part, every section, card and piece with an id, and
the first forty links within the site. The widget then adds the focus from the site's rule for it, `SiteFocuses`,
which lives in the web project.

The server can already read a page too. The site's API renders any page to HTML for search engines
(`PagePrerenderer`), and the site's index of places reads that HTML by the same marks the widget reads in the
browser (`SitePlaces`, `PlaceReader`, `HtmlTag`), served at `/v1/site/places`. The site's Docker image has no
browser in it.

The guide's own eval has one conversation and it names the page `/`. Its recordings in git were made without the
page, so they go out of date the moment a run sends one.

## Design

### 1. In plain words

A conversation in an eval file says which page its visitor is on. Before the run asks the first question of that
conversation, it asks the site for that page, the way a visitor's browser would have read it. The site renders the
page on the server and answers with its address, title, words, places, links and focus. The run puts that on the
first message, and the agent reads it as it reads a visitor's.

A live run keeps the page it sent beside the agent's recorded answers. A replay sends that kept page and asks the
site for nothing, so it gives the same answers at no cost, however the site's pages have changed since.

### 2. A page, read on the server

![The types: a page reader that turns a rendered page into the wire's page, the route over it, the run's page client, and the player that sends the page with the first ask](diagrams/F126.3.3-the-page-a-conversation-names-interface-design.svg)

A new reader in the API takes a rendered page and gives the page as a message carries it: the wire's own
`PageRequest`, so nothing of the wire is typed twice (ADR 0045).

```csharp
internal static class PageReader
{
    public static PageRequest Read(RenderedPage page, string address, string under, string? focus);
}
```

It follows the widget's module rule for rule, and each rule has its test:

| Part | The widget's rule | On the server |
|---|---|---|
| Address | The browser's path | The address asked for |
| Title | The document's title | The rendered page's title |
| Text | The visible text of `main`, white space folded | The words of the rendered `main`, tags and what a style or script holds gone, folded |
| Places | Every section, card and piece with an id, with its heading | The places reader the site's index already uses |
| Links | Links within the site, each once, by address and words cut at 60, the first 40 | The same, read from the rendered `main` |
| Focus | The site's rule for the address | The same rule, from the shared contract |

Three things a render can't know stay out: the section on the visitor's screen, the card they opened and the piece
they selected. Each needs a screen. The text is not cut here, since the cap is the API's, in one place (ADR 0104).

The words-of-some-markup rule is private to the places reader today. It becomes a named type both readers ask
(ADR 0123), and the places reader's own tests hold that nothing changed for it.

The focus rule, `SiteFocuses` with its `FocusPart`, moves from the web project to `LouisAgent.Composition`, the
contract the web and the API both reference. The builder a site names its focuses with stays in the web. The
widget keeps asking the same rule from its new place.

### 3. The route

```
GET /v1/site/page?address=/identities     200, the page as PageRequest
                                           404, when the site has no page at that address
```

It is mapped where the site's pages and its search are mapped (`MapLouisAgentSite`), so a host with no site has no
such route. It is open, as `/v1/site/places` is: what it answers is the site's public words. A page is rendered
once per address and kept for the host's life, the way the site's index keeps its places, so a run with three
repeats renders a page once and nobody can make the host render on every call.

The pattern is Fowler's Remote Facade, picked over a seam handed to the run and over the API filling the page in.

### 4. The run asks, sends and keeps

![One conversation that names a page, played live: the run asks the route, keeps the page under its trial, and sends it with the first ask](diagrams/F126.3.3-the-page-a-conversation-names-communication-a-live-play.svg)

```csharp
public sealed class PageClient(HttpClient http, ReplayStore? recordings)
{
    public Task<PageRequest> FindAsync(string address, RunTrial trial, CancellationToken cancellationToken = default);
}

// SessionClient
public IAsyncEnumerable<SessionEvent> SendAsync(string session, string message, PageRequest? page = null, ...);
```

`PageClient` is a small client beside `SessionClient`, over the same HTTP client the run asks the agent with. On a
live play it asks the route and saves the answer under the play's trial in the replay store, beside the agent's
and the judge's answers. On a replay it reads the kept page back and never calls the route.

The player sends the page with the first ask of a conversation that names one, and with no later ask, which is what
the widget does for a visitor who stays on one page. A conversation that names no page is played as today.

The page is saved with the store's own `SaveAnswerAsync` and found with `FindAsync`, under an ask that says what it
is. Whether that ask is the existing kind for a fetch or a kind of its own is a small call for step 5 to show: the
store writes the kind's name into its files, so a new kind changes no file that is there.

### 5. When there is no page

A run stops and says why, as it does when the judge can't mark. That is the harness failing, not the agent, so it
is never a failed conversation.

| What happens | What the run says |
|---|---|
| The site has no page at the address | The run could not finish: the page it asked for is not a page of this site, with the address |
| The host maps no site | The same, since the route answers 404 |
| A replay finds no kept page | The run could not finish: the recording is out of date, as for a model's answer |

A run's `PageSent` is true once a page was sent with any conversation. The run page already has both lines: for
such a run it says the agent was asked with the page a visitor's message carries, and no page of the admin changes.

### 9. What is reused

No new package and no new project. The render is `PagePrerenderer`. The places are `PlaceReader` and `HtmlTag`. A
page is found by its address with `SiteRoutes.PageFor`, and its places sit under `SiteRoutes.PlacesUnder`. The
answer is the wire's `PageRequest`, and the prompt's block is the API's `PageBlock`, untouched. The kept page is in
the engine's `ReplayStore`. The run's stop is the runner's own, with `StoppedBecause`.

### 10. The small calls this plan makes

These were too small for a card. Approving the plan approves them, and any of them can be changed with a word.

| The call | Why |
|---|---|
| The route answers the wire's `PageRequest`, not a reply record of its own | The run hands it on as it is, and one record means the two can't drift (ADR 0045) |
| The route is open, with no key | It answers what the site shows anyone, as the search route beside it does |
| A page is rendered once per address for the host's life | A site's pages change only with a deploy, and the site's index already works this way |
| The page goes with a conversation's first ask only | That is what the widget does for a visitor who stays on a page |
| The text is not cut by the reader | The API cuts it at 6,000 characters where it builds the prompt, in one place |
| What needs a screen is left out: the section in view, the open card, the selected piece | His pick was all a render can know |
| An address the site doesn't have stops the run | It is the eval file or the host that is wrong, not the agent |
| The address in the file is as the reader checks it today, starting with `/`, with no place inside a page | A place on a page is a screen's matter, and the file's schema stays as it is |
| The conversation page does not show the page that was sent | It would need the page in the run's file, which was the option not picked. The run page says a page was sent |

### 11. What this child leaves out

Starting, following, replaying and stopping a run from the admin are F126.3.4's. Flips, re-grade and the
comparison are F126.4's. The guide's new evals, which use more pages than `/`, are F126.5's. A page of another
site, fetched from the web, is not planned: an eval's page is a page of the host's own site.

### Step 3: a rendered page, read as a message carries it

The tests come first, in `PageReaderTests`, over small pages of markup written in the test. The title is the
rendered page's. The text is the words of `main` only, with a script's and a style's content gone, entities
decoded and white space folded. The places are the sections, cards and pieces with an id, each with the heading
the places reader gives it. The links are those within the site, each address once, their words cut at 60, at most
40, and a link with no words is named by its address. The focus is the one handed in, and none when the site names
none. A page with no `main` gives the words of its whole body. The section in view, the open card and the selected
piece are never set.

Then the code: `MarkupText` taken out of `PlaceReader`, with the places reader's tests still green, and
`PageReader` with `PageLinks`.

Run `LouisAgent.Api.Tests`.

### Step 4: the route

The tests come first, in `SitePageRouteTests`, over the API's test host with a small site. `GET /v1/site/page`
with a page's address answers that page, with its focus by the site's rule. An address the site has no page for is
404, and so is no address. A place inside a page, such as the landing's sections under the home word, answers the
page that holds it. Asked twice, a page is rendered once. The route needs no key.

Then the code: `ReadPages` and `SitePageRoute`, mapped in `MapLouisAgentSite` beside the search, and the route's
line in the API's design doc.

Run `LouisAgent.Api.Tests`.

### Step 5: the run can ask for a page, and send one

The tests come first. `PageClientTests`, over a handler that answers and a replay store in a folder the test makes:
a live play asks the route for the address and gets the page; the page is then in the store under the play's
trial; a replay gets the kept page and the handler is never called; a replay with no kept page throws the
out-of-date error the model's miss throws; a 404 throws `PageMissingException` with the address. In the session
client's tests: a message sent with a page carries it in the body, and one sent without leaves the key out, as the
wire's rule is.

Then the code: `PageClient` with `PageMissingException`, and the page on `SessionClient.SendAsync`.

Run `LouisAgent.Evals.Tests`.

### Step 6: a conversation's page goes with its first ask

The tests come first, in the player's and the runner's tests. A conversation that names a page asks for it once
and sends it with the first ask and with no other. A conversation that names none asks for nothing and sends
nothing. Three repeats ask under three trials. A missing page stops the run as could not finish, with the address
in its reason, and the conversations graded before it are kept. A run that sent a page says `PageSent`, and one
that sent none doesn't. In the eval routes' tests, a run started through the route against a host with a site
sends the page.

Then the code: the player takes a `PageClient`, the runner catches the missing page as it catches a judge that
can't mark, and `RunWork` builds the client over the HTTP client it already has.

Run `LouisAgent.Evals.Tests` and `LouisAgent.Api.Evals.Tests`.

### Step 7: a live run of the guide, and its recordings made again

`GuideEvalReplayTests` is the test that comes first, and it is red already once step 6 is in: the guide's one
conversation names `/`, and the recordings in git hold no page.

Then, on Louis's go, since it spends real money: one live run of the guide's eval on this PC, one conversation at

Then the free check by hand, with `/check-a-page`: on three pages of the site run on this PC (the landing, a page

## Verification

Every step's tests are named in it. Before the pull request, `main` is merged in and the full suite runs in the
pull request's checks, with Core's rule tests run here first. One paid run, in step 7: one conversation, once, on
