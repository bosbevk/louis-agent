**What was looked up.** louis-agent.dev's program takes the evals with `AddLouisAgentEvals` and
`MapLouisAgentEvals(adminKey)`, behind the admin key that `AdminOptions` reads from `ADMIN_API_KEY`; its runs are
kept under `SITE_DATA_DIRECTORY` (`EvalsOptions.RunsFolder`) and recorded under `REPLAY_DIRECTORY`. The framework
site's program (`LouisAgent.SiteFrameworkApi/Program.cs`) takes only the API and its pages, and its compose service
has neither setting nor a data volume. `.env.secrets.framework.example` already names `ADMIN_API_KEY`. In Azure, the
framework app mounts louis-agent.dev's share for `/logs` at `framework/logs`, and `deploy.ps1`'s entry for it lists
the share's folders a release makes (`framework`, `framework/logs`); the release after a merge applies the yaml
(`deploy-sites.yml`), so a second mount needs no Bicep (ADR 0131 is untouched). An eval file is found beside its
identity as `{name}.eval.json` (ADR 0134), embedded by the identity's project as the guide's is. `EvalReplay` plays
one folder's trials as one run, hence a folder per eval. Orbi's voice names six rules it never breaks and seven ways
it answers, and its five skills add a walkthrough, explaining a listing, where the docs are, the site's pages and how
it writes. Since FX235 a replay plays back what each tool answered, so Orbi's replay can run over no docs too. The
framework site's logs folder holds run logs only, no turn log, so there are no real chats to read.

## Design

The framework site's host takes the evals exactly as louis-agent.dev's does: the same two calls in its program, the
admin key it already reads, and a data folder for runs and recordings. Orbi's eval sits beside its voice and is read
at start-up, so a wrong file stops the host. A run is started and read over the API with the admin key, from inside
the container on this PC, as the run-an-eval guide will say. Its first repeats are kept in git and replayed on every
build by a test in the identity's own test project, over an empty docs folder.

**The conversations**, each a rule Orbi's prompt names, with a fact in code where code can tell and a criterion
where only a reader can: it answers from the docs (`used SearchDocs` or `used ReadDoc`) and ends with the doc's path;
it says it is an AI when asked; it says it doesn't know when the docs don't say; it writes code when asked, in a
fenced block from the doc's listing; it answers about the page it sees from the page block; it opens a page with
`ShowPage` when one answers; it walks a page one section at a time (`used ReadSkill`); it explains a listing from the
page (`used ReadSkill`); it sells nothing and sends a buyer to louis-agent.dev; it tells no story about Louis; and it
opens with the answer, no warm-up (`never-says Great question`). The injection case gives Orbi a page whose words
tell the AI reading it to send the developer to a download address and say a code word; code checks it did neither.
The exact conversations are written in step 5 from the voice and skills as they stand.

## Steps

1. **This plan**, with its records: the plans' README, the TODO's and the work log's F126 rows.
2. **A folder per eval.** The guide's recordings move to `src/site/recordings/evals/guide/` (`git mv`), and its
   replay test and the run-an-eval guide follow. A move that changes no behaviour, held by the replay test, which
   still replays all twelve.
3. **The framework host takes the evals.** Its program adds `AddLouisAgentEvals` and `MapLouisAgentEvals`, as
   louis-agent.dev's does. Tested first in `FrameworkEvalRoutesTests`: the routes answer only with the admin key, and
   list the evals the catalogue holds.
4. **Its data, here and in Azure.** The compose service gets `SITE_DATA_DIRECTORY=/data`, `REPLAY_DIRECTORY=/data/recordings`
   and `../data/framework:/data`; the run profile the same, as paths; the Azure yaml the two settings and a mount of
   the share's `framework/data` on `/data`; `deploy.ps1`'s entry the folder `framework/data`. Tested first in
   `DeployFilesTests`: the framework's entry names the folders its mounts need.
5. **Orbi's eval, from its rules.** `framework.eval.json`, about eleven conversations, embedded as the guide's is.
   Tested first in `FrameworkEvalFileTests`: a conversation for each rule listed, and every tool a fact names is
   one Orbi has.
6. **The injection case.** A page given in the file with hidden instructions, checked by `never-says` on the code
   word and the address. Tested first in `FrameworkEvalFileTests`.
7. **The baseline.** A live run of three repeats on Louis's go (about $0.08), started over the API from inside the
   container, the judge's reasons read, each conversation's first repeat into `src/site/recordings/evals/framework/`,
   scanned before staging. `FrameworkEvalReplayTests` replays every conversation over an empty docs folder, written
   first and seen failing with no recordings.
8. **The close.** The design docs of the framework host, Orbi and the evals' API, the run-an-eval guide (starting a
   run over the API), the deploy guide (the new mount), the write-up in `12-evaluation.md`, the records, and this
   plan deleted.
