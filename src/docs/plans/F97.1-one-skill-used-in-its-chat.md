# F97.1 One skill, used in the chat that made it

A plan: how the agent's tools and skills become one kind of skill in our standard, and how a chat uses the skill it
made at once, through one door that never changes its tool list. It is the first child of
[F97](F97-a-skill-usable-in-its-chat.md), and it holds what that plan first cut into two children: the shape, and the
draft, the door and the approval. Each step is one commit with its test, written first and seen failing.

![F97.1 at a glance: one shape, the draft and the door, then the old gone and the proof](diagrams/F97.1-one-skill-used-in-its-chat-overview.svg)

## Context

Louis walked FX4 on the coding agent at `:5082` on 2026-11-26 and found that a tool a chat makes can't be used in that
chat: "if a chat creates a tool it should be able to fucking use it, not only in a new chat". F97's plan holds the
design he said yes to and the picks behind it. Four more were made before this plan, each recorded under F97's
*Approved during the build*: a skill's parameters are `parameters.schema.json` beside its `SKILL.md`; the script it
runs is named in `metadata.script`, its language from the extension; F97.1 and F97.2 are built as one child; and the
arguments are checked by our own code, with no package. And: "when the core creates a skill it must be in our
standard, it must use the write skill skill. YAML".

What the code holds today was read for this plan. `PromptHeaders` already reads a `SKILL.md`'s YAML for an identity's
skills, strictly, and names the folder as the skill's name. `PythonRunner`, `PowerShellRunner` and `BashRunner` (in
`LouisAgent.Composition`) already take JSON on stdin, which is how an agent-built tool runs today. `ISkillProvider`
does two jobs: the system prompt's text (`Documentation`) and the runnable skills (`Skills`, parsed from code fences).
Only the agent's own function skills use the second; the orchestrator's runbooks have no code to run. About 50 files
name `CreateTool`, 36 `ExecuteSkill` and 24 `CreateSkillFile`, the coding agent's `toolsets/self-extension.md` among
them.

## Design

### 1. A skill on disk

```
skills/word-count/
├── SKILL.md                  name, description, metadata.script; the body says what it is for
├── parameters.schema.json    a JSON Schema object: properties, each with a type and a description; required
├── examples/example.json     the call it was proved with when it was made, and the answer it gave
└── scripts/count.py          reads one JSON object from stdin, prints its answer
```

```yaml
---
name: word-count
description: Counts the words in a piece of text. Use when asked how many words a sentence or passage has.
metadata:
  script: scripts/count.py
---
```

`SKILL.md` is exactly the Agent Skills spec: `metadata` holds plain strings, and nothing else of ours is in it. The
reader takes the name from the folder, as `PromptHeaders` does for an identity's skills, and refuses a skill with what
to change: a header that won't read, a missing script, an extension that isn't `.py`, `.ps1` or `.sh`, a schema that
isn't an object of typed properties. Drafts live in `skills/drafts/{name}/`, which git ignores.

### 2. Arguments are checked by our own code

`SkillArguments` takes the schema and the call's arguments and lists the problems: a required property missing, a
property the schema doesn't name, a value whose JSON kind isn't its property's `type` (`string`, `number`,
`integer`, `boolean`, `array`, `object`). That is all a skill's flat parameters use; a schema with anything more is
read, and the rest of it is left to the script. A call with problems never runs, and its answer names each one.

### 3. Who reaches what

One tool reaches every skill: `UseSkill`, in every chat's list from its first turn, as Claude Code's `Skill` tool is.
No skill is ever a tool of its own, so the list stays the size it is however many skills there are, and each skill
has one way in. The engine reads the approved skills into a `SkillLibrary` when it starts or reloads, and when a chat
starts, `UseSkill`'s description lists every approved skill by its name and its one-line description; that
description is frozen with the chat's tools (FX4), so a skill approved later is reachable in an open chat but listed
only in the next. `UseSkill(name)` with no arguments reads a skill, its instructions, its parameters and its example,
as the spec loads a skill's body only when it is needed; with arguments it checks them and runs the script.

`CreateSkill` is given the files and one example call. It writes the draft, runs the example, and keeps the draft only
if the run succeeds, saving the call and its answer in `examples/example.json`; otherwise nothing is kept and the
reply shows what failed. It tells the library which chat made the draft, and that chat alone reaches it. `/approve`
moves a draft's folder up and shows its example, `/reject` deletes it, and the host keeps what each did and puts it in
front of the person's next message.

### 4. The agent writes a skill in our standard

Core ships `write-a-skill` for the agent, on demand: the standard our own `write-a-skill` holds for Claude Code, cut
to what an agent-made skill needs. The name is a verb and what it acts on, in kebab case, at most 64 characters. The
description is in the third person, what it does and then when to use it, under 1,024 characters, with no colon and
space that would break the YAML. The body says what the skill is for and what it gives back. The script reads one
JSON object from stdin and never builds a command from it. `CreateSkill`'s description tells the model to read it
first, and `SkillReader` refuses what doesn't hold, saying what to change. It is one of core's built-in skills,
`skills/write-a-skill/SKILL.md`, beside the others (section 5).

### 5. A toolset's guide is a built-in skill

Core's `toolsets/agents.md` and `toolsets/self-extension.md`, and the twelve guides in the packs, are skills that a
toolset always loads; only their shape differs. In the standard a skill is always a folder, and whoever uses it
decides when it loads, as a Claude Code subagent preloads the skills its `skills:` field names. So each project keeps
its built-in skills in `skills/{name}/SKILL.md`, and a toolset names the skill it always loads; `ToolsetDefinition`'s
`GuideFile` becomes that skill's name. The `skills` toolset's guide, `self-extension`, is named for its toolset. The
text the model reads doesn't change, so the golden files don't either.

## Steps

1. **A skill read from its folder.** `Skill`, `SkillState` and `SkillReader`: a folder becomes a skill or is refused
   with a reason. Test: `SkillReaderTests`, a good folder and one per refusal.
2. **`metadata.script` in the header.** `PromptHeaders` takes the key as a string. Test: a header with it reads; an
   identity's prompt still refuses an unknown key.
3. **The arguments checked.** `SkillArguments.Problems`. Test: each kind of problem named, a good call none.
4. **The runner.** `SkillRunner` runs a skill's script by its language with the arguments as JSON on stdin, in the
   workspace, through the runners core has. Test: the language dispatch over a fake; a real run of each language in
   the integration tests, skipped where the language isn't installed.
5. **Every path on `SkillFiles`.** The skill's folder, its draft's, the drafts folder, the schema file; the old
   function and `tools/` paths gone. Test: `SkillFilesTests`.
6. **The library of approved skills.** `SkillLibrary` reads `skills/*/` but not `drafts/`, logs and skips a skill
   that won't read. Test: a temporary folder with two skills, a draft and a broken one.
7. **The approved skills listed in the door.** `SkillListing` gives one line per approved skill, its name and its
   description, in a fixed order; `UseSkill`'s description carries it, built when a chat starts and frozen with its
   tools; no skill is registered as a tool of its own, in place of `AgentBuiltTools`' loading. Test: a new chat's
   `UseSkill` lists an approved skill, an open chat's description doesn't change when one is approved, and the
   number of tools sent doesn't grow with the skills.
8. **`CreateSkill`, proved by an example.** It writes `skills/drafts/{name}/` from the `SKILL.md`, the schema, the
   script and one example call it is given, reads it back with `SkillReader`, runs the example, and keeps the draft
   only if the run succeeds, saving the call and its answer in `examples/example.json`. Test: a good skill drafted
   with its example; a bad file refused, and a script that fails its example refused with its error, nothing left on
   disk in either case.
9. **A draft belongs to its chat.** The library keeps which chat made each draft; `Find` gives a chat its own drafts
   and every approved skill. Test: a second chat can't find the first chat's draft.
10. **`UseSkill`, the door.** In every chat's list from its first turn; with a name alone it returns the skill's
    instructions, parameters and example; with arguments it finds the skill for this chat, checks them and runs it;
    a wrong call's answer gives the parameters; an unknown name lists what this chat may use; a rejected one is
    refused. Test: a chat makes a skill, reads it and uses it in the same turn, and the tools it sends never change.
11. **`/skills`, `/approve`, `/reject` on folders.** In place of `/tools`; `/skills` and `/approve` show each draft's
    example and its answer; approve moves the folder up, reject deletes it. Test: each command's answer and what is
    on disk after.
12. **The note on the next message.** The host keeps what `/approve` and `/reject` did and puts a short note in front
    of the person's next message; it is appended, never an edit. Test: the next request's last user message carries
    the note, and the earlier messages are unchanged.
13. **`ListSkills` and `ReloadSkills`.** `ListSkills` in place of `ListAgentTools`; a reload reads the library again
    for the next chat. Test: a dropped-in skill appears after a reload, and the open chat's tools don't change.
14. **The old ways gone.** `CreateTool`, `CreateSkillFile`, `ExecuteSkill`, `AgentBuiltTools`, `ScriptTool`,
    `ScriptToolDefinition`, `ScriptToolParameter` and `MarkdownSkillLoader`'s runnable half are deleted;
    `ISkillProvider` gives the prompt's text only; `SkillLoader` no longer discovers function files. Test: a list of
    the deleted names, changed first and seen failing while they are there.
15. **The guides become built-in skills.** Core's two guides and the packs' twelve move to `skills/{name}/SKILL.md`,
    each named for its toolset (`self-extension` becomes `skills`); a toolset names the skill it loads; the loader
    reads it from there. Test: the layout test, changed first and seen failing on a flat guide, and each toolset's
    prompt the same text as before.
16. **The agent's `write-a-skill`.** One of core's built-in skills, in our standard, loaded on demand, named in
    `CreateSkill`'s description. Test: its header reads, and `CreateSkill` refuses a description with a colon and
    space, as the skill says.
17. **The prompts and the goldens.** The `skills` toolset's skill, the Shell pack's `python` skill and every tool text
    rewritten for the one kind and the door; the golden files regenerated and their diff read.
18. **The demo's skills folder.** Its README, `.gitignore` for `drafts/`, and the two skills the walk-through
    approved moved into the new shape or deleted, on Louis's word.
19. **The docs.** ADR 0033 amended as Louis approved; ADR 0028's mention, the core design doc, `add-a-skill.md`,
    `build-a-pack.md`, `build-an-identity.md`, `common-errors.md`, architecture 05, 06 and 12, core's `CLAUDE.md`
    and `.claude/rules/prompts.md`, and their pictures.
20. **The walk-through.** On the coding agent at `:5082`, on Haiku 5.5, on Louis's word: a chat makes a skill and
    uses it in the same answer; `/approve`, then a message, and the model knows; a new chat finds it listed in
    `UseSkill` and calls it; `/reject` refuses it; no 400. Its cost reported.
21. **The close.** The write-up's section, the work log, the TODO, and the plan's lasting parts moved before it is
    deleted.

## Verification

Each step runs the tests of what it touched, `LouisAgent.Core.Tests` among them where files move. The full suite runs
after `main` is merged in, before the pull request. Step 20 is the one paid check, a few cents. **Done when** an
approved skill in the YAML standard is listed in a new chat's `UseSkill` and runs through it with JSON on stdin; a
chat makes a skill, proved by its example, and uses it in the same answer on Haiku 5.5 with no 400; the model knows
of an `/approve`; the number of tools a chat sends doesn't grow with its skills; and nothing in core names `.tool.md`,
`agents/functions`, `CreateTool`, `CreateSkillFile` or `ExecuteSkill`.

## Concepts

Steps 1 to 7 are *20 Extensibility*: one shape for what extends the agent, read from a published standard. Steps 8
to 13 are *4 Tool design* and *9 Sessions and state*: a fixed door that keeps a session's tools stable while what it
can do grows, and telling the model what changed outside its view. Steps 15 and 16 are *3 Prompt engineering*: one
shape for every skill, and a procedure the model follows, held by a check in code. Step 20 is *18 Testing and
shipping*.

## Approved during the build

**2026-11-26, the agent's skills live under `Skills/Headers/Agent/`, not `Skills/Library/`.** `ArchitectureTests`
(CL13) lets a folder inside `Skills/` use only the top, `Messages/` and `Languages/`, never a sibling, and the reader
needs `Skills/Headers/`' `PromptHeaders`. Louis picked putting them under `Headers`, as an identity's skills already
are (`Skills/Headers/Identities/IdentitySkill`), over making `Headers` a shared folder and over a top-level folder of
their own. So step 1's types are in `Skills/Headers/Agent/` and its reader in `Skills/Headers/Agent/Reading/`, with
their tests mirrored; the later steps' types go below `Skills/Headers/Agent/` too (`Arguments/`, `Running/`, `Library/`),
where the section 6 map says `Skills/Library/` or `Skills/Running/`. Step 2 was built before step 1, which needs it.

**2026-11-26, the engine gets a builder, as a step after step 4.** Louis tested the coding agent at `:5082` on this
repository, and it began an `AgentEngineBuilder` (the Gang of Four's Builder: `AgentEngine.Builder(skills, model,
options)`, a `.WithX(...)` call per optional part with the constructor's default, then `.Build()`), the cure
[Refactoring.Guru](https://refactoring.guru/design-patterns/builder) gives for a constructor of many optional
parameters, as `AgentEngine`'s is. Louis: "can you continue making the agentbuilder in this feature"; then his pick of
a step now, over a step after the skill steps and over a cleanup of its own. So step 4b finishes it: its test first
for what the agent wrote without one, the repo's rules on its files, and every caller building through it. Five of
its calls (`WithSelfExtension`, `WithSkillsDirectory`, `WithReservedToolNames`, `WithSkillReloader`, and the
`LoadApprovedTools` after it) are about what F97.1 replaces, and change again in steps 6 to 14.

**2026-11-26, the door is only in chats with the skills toolset.** Section 3 said every chat; put there, `UseSkill`
changed every agent's tools, and the guide's, the framework Orbi's and the triage team's recorded evals stopped
replaying, while the sites' agents have no skills to reach. Louis picked giving the door only to the chats whose agent
can make and keep skills, the skills toolset, as `CreateSkill` will be, over every chat with the evals re-recorded now
and at the end, and over every chat with one re-record at the end. The sites' recordings stay as they are. Step 10 was
cut in two: 10a the door's behaviour (`SkillDoor`), 10b the door as `UseSkill` in a chat, its chat named by the turn's
`TurnTools` scope, its approved skills listed after its description by a Decorator.

**2026-11-26, the triage eval is re-recorded once, after step 14.** The demo's host gives every chat the skills
toolset, so the triage team's chats get the door in 10b and their tools change again in step 14. Louis picked one live
re-run after step 14, on his word, over re-recording now and again, and over taking the skills toolset from the triage
team's sessions. So `TheTriageEval_ReplayedFromItsRecordings_MeetsEveryFact_InEveryConversation` is red from 10b until
then.

**2026-11-26, the note is a system-reminder in the chat the command was typed in.** Louis: "do research how is it
suppose to work". Claude Code tells its model what changed outside its view in a `<system-reminder>` added to the next
user message of the session where it happened, never in the system prompt, so the cached prefix holds
([an analysis](https://y-agent.github.io/inside-claude-code/14-hidden-costs-context-manipulation.html)); Pydantic AI
follows the same tag ([Pydantic](https://pydantic.dev/docs/ai/harness/system-reminders/index.md)); Anthropic's API also
offers a mid-conversation system message on some models
([Anthropic](https://platform.claude.com/docs/en/build-with-claude/mid-conversation-system-messages)). Louis picked the
reminder in the chat it was typed in, over every open chat and over Anthropic's system message: `HandleUserCommand`
takes the chat, and the CLI, the API and ACP pass it.

**2026-11-26, no `ListSkills` tool.** `UseSkill` already answers a name the chat can't use with every skill it may use,
read fresh, and its description lists the approved ones, so a `ListSkills` tool would be a near-duplicate, which the
research says makes a model pick the wrong tool more often. Louis picked dropping it, over keeping it and over
`UseSkill` with no name listing. So `ListAgentTools` goes in step 14 with nothing in its place, the door's description
says a name it can't use gets the list, and step 13 is `ReloadSkills` alone: a reload reads the skills folder again.
