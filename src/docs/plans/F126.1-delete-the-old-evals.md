# F126.1 Delete the old evals

A plan: how today's evals leave the repository whole, so the new ones are built into empty folders under their
real names. It is the first of the five children of [F126 Evals, redesigned](F126-evals-redesigned.md), which says
what the new evals are and why. This file says what this child removes, in which order, and gives its eleven steps.
It builds nothing new for the evals.

![Four moves, from the outside in: the sites stop naming the evals, the pages and the studio go, the harness goes, and the record and the words are made true; the engine's replay, the sessions API and the ledger stay](diagrams/F126.1-delete-the-old-evals-overview.svg)

## Context

Louis, 2026-11-09, of the evals as they are: "forget the current evals, we will redo it all". The parent plan
deleted them last, in its fourth child, and built the new ones beside the old in the meantime. On 2026-11-22 the
plan was reviewed, and one gap was that order: the old harness holds names the new parts need (`EvalFile` and
`EvalRun` are two), and it sits under every rule test while the new code is written. Louis picked
"1. Delete first" that day, and then: "start writing the plan, so long for step 1" and "I will implement each step
via a promt you provide in rider". So this child is first, it is numbered F126.1, and the old F126.1 to F126.4
become F126.2 to F126.5. Each step below has a prompt for Rider, kept beside the review in the project's files.

It comes after CL68.3 and CL69, which Louis is finishing. Both rename words inside files this child deletes, so
they land first and this child starts from the `main` they leave.

**What was read.** Everything below was read on `main` at commit `813dcf0` (2026-11-22): every project file that
references an eval project, every file outside the eval projects that uses an eval namespace, the rule tests that
carry lists of projects, the two sites' programs and areas, the demo's Docker and settings files, the live site's
deploy script, the docs that link the eval docs, and the nine ADRs about evals. The lists in *Design* are that
reading. `main` will have moved by the time step 2 starts, so step 2 opens by reading two of them again.

**Five choices were put to Louis first**, each on a card with three options, on 2026-11-22. The last two came
from checking the plan against the code:

- **What survives.** The parent plan said four small parts of the old evals are kept and built on: the client that
  talks to the sessions API over HTTP (`ISessionClient`, `HttpSessionClient`) and two judge helpers
  (`ConfiguredJudge`, `NoTemperatureChatClient`). His pick: "1. Delete everything". They go with the rest, and the
  child that builds runs copies the client back from git with its test first. The reason is Fowler's Yagni: "some
  capability we presume our software needs in the future should not be built now", and code nobody calls has a
  cost of carry, since "this complexity makes it harder to modify and debug that software"
  ([Yagni](https://martinfowler.com/bliki/Yagni.html), 2015, read 2026-11-22).
- **The record.** Nine ADRs describe the old evals. His pick: "1. In F126.1, from your picks". One new ADR is
  written in this child from the decisions already taken, and the nine say *Superseded by* it in the same step.
  That is our own rule (`src/docs/adr/README.md`: "write a new ADR that supersedes it") and how Nygard, who first
  described these records, does it: "If a decision is reversed, we will keep the old one around, but mark it as
  superseded" ([Documenting Architecture Decisions](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions),
  2011, read 2026-11-22). Its lines are in *The new ADR, proposed* below, and he said yes to them that day.
- **The live words.** louis-agent.dev's trust page has a tile marked done, "Checked on evals". His pick:
  "1. One open tile that says so". The page's two eval tiles become one, marked not built yet. That is ADR 0100:
  the site "shows what's planned as planned".
- **The evals family on the framework's site.** That site tells the framework as five families, and one of them
  is the evals, with its four projects. After step 8 the family ships no project. His pick: "1. It stays, being
  rebuilt". The family keeps its place on the page, lists no project, and says it is being rebuilt, as the trust
  page will and as the site's *Cost and evals* page already does. It is ADR 0100 again.

- **The trust page's words.** Changing the tile touches the trust page's content, 35 facts held as five lists of
  text in C#. ADR 0132 says a page's words come from a dictionary factory, and that "a page converts when it is
  touched". His pick: "1. The whole page first, own step". Step 10 moves the page to the factory and changes no
  word, and step 11 changes the tile. That is the order Kent Beck gives, as Fowler quotes him: "make the change
  easy, then make the easy change"
  ([An example of preparatory refactoring](https://www.martinfowler.com/articles/preparatory-refactoring-example.html),
  2015, read 2026-11-22). It is also how the first page was converted, *Build your own*, in a commit of its own
  (`c9467b1`). It makes this plan eleven steps, one over the "about ten" a plan holds.

**What could not be confirmed, and the step that will.** Whether the admin records in
`LouisAgent.Api.Contracts/Admin/Checks` and `Admin/Trends` have a user once the studio is gone: today only the
studio, the eval pages and one test of the contracts project name them, and step 7 asks Rider's *find usages*
before it deletes either. What the case `EVALS_MONGO_URL` in `DeployFilesTests` holds: step 11 reads the test
before it touches the deploy script. No test holds a markdown link from one doc to another (searched on
2026-11-22), so a link from an old ADR into a deleted doc is left as written: an accepted ADR is not edited, and
git keeps what it points at.

## Design

### 1. What goes, and what stays

Sixteen projects go. Six are the framework's eval code: `LouisAgent.Evals`, `LouisAgent.Evals.Checks`,
`LouisAgent.Evals.Protocol` and `LouisAgent.Evals.Runner` under `src/evals/`, with the template folder beside
them, then `src/hosts/LouisAgent.Api.Evals` (the studio's API) and `src/web/LouisAgent.Web.Evals` (the eval
pages). Six are their test projects, under `src/tests/evals/`, `src/tests/hosts/` and `src/tests/web/`. Two are the
demo's: `LouisAgent.Identities.Triage.Evals`, which holds the triage team's three evals, and
`LouisAgent.CodingEvalRunner`, the program that ran them. The last two are small programs the API's tests started
as a child process, both under `src/tests/hosts/`: `LouisAgent.Api.TestRunner`, the real runner with a template
eval, and `LouisAgent.Api.StandIn`, which stands in for the runner.

What leans on those projects from outside is small, and it is the reason for the order of the steps:

- **The two sites that name the area.** The starter and the code-review demo each call `.Evals()` in their areas
  and `app.MapLouisAgentEvals(host)` in their API's program. louis-agent.dev and the framework's own site name
  neither, so nothing a visitor uses today changes when the area goes.
- **The API's tests.** `LouisAgent.Api.Testing`, the library every API test starts from, wires the studio's
  stores into `ApiTestHost` and holds ten contract files for them. `LouisAgent.Api.IntegrationTests/Evals` holds
  fifteen files that test the studio. And one test of the harness, `SampleBodyShapeTests`, reads a type of the
  studio, so the harness's tests reference the studio too.
- **The agent API itself.** `LouisAgent.Api.csproj` references `LouisAgent.Evals.Protocol` and
  `LouisAgent.Evals.Checks`, and no file in the project uses a type from either. It also opens its internals to
  `LouisAgent.Api.Evals`, as `LouisAgent.Core.csproj` does.
- **The admin's eval records.** `LouisAgent.Api.Contracts/Admin` holds the records the studio sends the eval pages:
  the folders `Drafts`, `Evals`, `Studio`, `Reviews` and `Runs` are used by nothing else. `Imports`, `Overview`,
  `Prompts` and `Screens` are used by the admin's other pages and stay.
- **One package.** `Microsoft.Extensions.AI.Evaluation` is referenced only by eval projects.

What stays is what the new evals are built on. The engine's replay (`ReplayStore` and `ModelReplayChatClient` in
`LouisAgent.Core`, and the web's recorders) is an engine feature and is not touched. The sessions API keeps its
`replay` field. The usage ledger is the only source of cost, as before.

![The seams a site and a test touched the evals through, and what happens to each; nothing is added to them](diagrams/F126.1-delete-the-old-evals-interface-design.svg)

### 2. The order: from the outside in

A project can only be deleted once nothing references it. So the steps go from the sites inwards. First the two
sites let go, and then the eval pages can go. Then the studio's own tests go, and after them the API's test
library has nothing left that needs its eval parts, so it lets go too. Only then can the studio's API go, with the
records only it and the pages used. The harness is last, because everything else stood on it. After every step the
solution builds and the tests of what was touched are green, so any step can be the last one of a day.

![Each part goes only after everything that references it has let go; the number in brackets is the step](diagrams/F126.1-delete-the-old-evals-architecture.svg)

### 3. One deleting step

Every step from 2 to 8 runs the same way, and it is still test first. The repo's rule tests carry lists of the
projects each folder holds (`SolutionLayoutTests`), of the packages the framework publishes (`PackagesTests`) and

test goes red because the project is still there. Then the references are removed, the project is deleted with
Rider's own tools, the build says what still leans on it, and the touched tests go green.

### 8. The new ADR, proposed

A new ADR needs Louis's yes before it is written, and he gave it to these lines on 2026-11-22, with the plan.
Its number is the next free one on the day step 9 is built (0134 on 2026-11-22). Its title: **An eval is one file of conversations, and the old evals are gone.** It records only what
he has already decided, on 2026-11-09 and 2026-11-22:

1. Today's evals are deleted whole and nothing is ported. No stored run is moved (ADR 0049).
2. An eval is one `{name}.eval.json` beside the identity it proves: conversations with turns, each turn with its
   own facts and criteria.
3. A fact is told in code, from a closed list parsed once into an enum. Everything else is a criterion that one
   model judge marks yes or no with a reason, one call per criterion.
4. A conversation passes only when every fact and every criterion of every turn is met in every repeat.
5. A person corrects the judge by flipping a mark. There are no label files and no percentage of agreement.
6. The eval part is a library a site's own API maps. A run asks the agent over the sessions API, like any app.
7. An eval file is read through the same file providers as prompts.
8. Carried over: a pack and an identity reference no eval project (from 0073), and a live run waits for Louis's go
   (from 0029).

It supersedes 0022, 0029, 0047, 0056, 0058, 0059, 0061, 0062 and 0073. Its consequences, said plainly: between
this child and F126.3 the repository can run no eval, the admin has no Evals area until F126.3 draws it, and the
first new evals are written in F126.5.

### 9. What this child leaves out

It writes no new eval code, not even an empty project: F126.2 makes `src/evals/` again. It does not drop any
database. The old runs live only in a developer's local `evals` database, since the live site never mapped the
studio, and Louis drops it by hand when he likes. It leaves Louis's CV as it is: its entry "Evals in C#" tells
what he built. It leaves `src/tools/rename-projects` as written, since that folder is the record of a rename
that ran once. And it leaves the parent plan's other picks of 2026-11-22 for the change that brings the parent
along.
