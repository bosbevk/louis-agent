# F171.1 A photo or a PDF reaches a tool

A plan: how the engine comes to take a photo or a PDF, keep it with the session, and let a pack's tool have a
model read it into a record. It is the first of the eight children of
[F171 The bill checker](F171-the-bill-checker.md), which says what was decided and why. This file says what this
child builds, then gives its ten steps.

![Four parts: the API takes a file as bytes, the session keeps it, a tool finds it by name, and the engine's reader has a model read it into the record the tool asks for, with the cost in the ledger](diagrams/F171.1-a-photo-or-a-pdf-reaches-a-tool-overview.svg)

## Context

Louis, 2026-11-22: "this feature is next", and then "nxt" for its first child. The bill checker reads a municipal
account from a photo or a PDF. Today the engine can't take either. This child is the engine's half of that, and it
is framework work: nothing in it knows what a bill is. Louis, 2026-11-22: "the engine should be generic ain't it,
it should not contain rules from packs". The bills pack that uses it is F171.2, in the product's own repository.

**What the code has today.** A message to the API may carry attachments, and an attachment is a name and a text
(`AttachmentRequest(string Name, string? Content)`). The API pastes each one into the prompt, cut at 100,000
characters, and the session keeps them by name so an asked agent can be handed one later. A user's turn reaches
the model as one string. The pack context, which is everything the engine offers a pack's tools, holds the
workspace, the web and the site's places, and no model. Two side jobs already call a model outside the
conversation: the summary of an oversized tool result and an eval's judge. Each runs under its own purpose in the
usage ledger. Nothing in the repository sends an image or a document to a model, and nothing asks for an answer in
a schema.

**What was read on 2026-11-22**, each at its source.

Microsoft.Extensions.AI gives a file to a model as `DataContent`, bytes with a media type, and
`GetResponseAsync<T>` asks for an answer that fits the JSON schema of `T` and gives it back as a `T`
([the library's docs](https://learn.microsoft.com/dotnet/ai/ichatclient)).

Claude reads JPEG, PNG, GIF and WebP images of up to 10 MB each, and PDFs. A PDF's pages each go in as text and as
an image, at about 1,500 to 3,000 tokens a page, and "All active models support PDF processing". A request to the
Messages API may weigh 128 MB ([PDF support](https://platform.claude.com/docs/en/build-with-claude/pdf-support),
[the API's overview](https://platform.claude.com/docs/en/api/overview)). Structured output works on every model
and takes no limits on a number's size or a string's length in the schema.

Haiku 5.5 costs $0.10 for a million tokens in and $0.50 out, and Sonnet 5.5 $2 and $10
([pricing](https://platform.claude.com/docs/en/about-claude/pricing)). A photo of a bill is at most about 4,800
tokens on the high-resolution tier, so a reading costs roughly a tenth of a US cent on Haiku and two cents on
Sonnet.

MCP deprecated sampling, the way a server asked its client's model for an answer, from its 2026-07-28 revision:
"Servers that need LLM capabilities can integrate directly with LLM provider APIs" (SEP-2577).

**What could not be confirmed.** The Anthropic package we use (12.53.0) holds the words for PDFs, the four image
types and a JSON schema, so its adapter looks able to send a file and ask for a schema. No run has shown it. Haiku
5.5's own page says it takes "Text and images", and says nothing of PDFs, of structured output or of the
high-resolution tier the parent plan names for it. Step 2 proves all of this with two live readings, and the plan
stops there if they fail.

**What Louis picked for this child.** On 2026-11-22 he picked how a tool gets a model to read a file: "A then", a
reader the engine offers, over handing a pack the engine's whole model client and over a pack bringing its own
model and key. His reasons on the way: "we can just pass our own", a pack with its own model would need "tool
ledgers", and the engine stays generic. The same day he picked which model does the reading: a
setting names it and it is the instance's own until someone sets it, over always the instance's own model and
over a pack asking for a size on each call. That is step 9.

## Design

### 1. The two things a pack may ask

A pack's tool gets two new things from the pack context. The first is the session's files: the tool gives a name
and gets the file, its type and its bytes. The second is a reader: the tool gives it a file, its instructions and
the type of record it wants filled in, and gets that record back. The reader knows a file, a schema, instructions,
a model and the ledger. What the record means is the pack's business.

Both follow the shape the pack context already has for the web. The contract sits in the small package a pack
references and the engine implements it, which is Fowler's Separated Interface. The reader is a Gateway in his
words, "An object that encapsulates access to an external system or resource": the pack never sees the model
client behind it. A host that has no session or no model gets an implementation that says so, as a host with no
website gets `NoSitePlaces`, so no pack and no test that exists today has to change.

![The pack context gains Files and Reader; each has the engine's implementation and one that says no](diagrams/F171.1-a-photo-or-a-pdf-reaches-a-tool-interface-design.svg)

```csharp
public interface ISessionFiles
{
    SessionFile? Find(string name);
    void Forget(string name);
}

public sealed record SessionFile(string Name, FileMediaType MediaType, ReadOnlyMemory<byte> Bytes);

public interface IDocumentReader
{
    Task<T> ReadAsync<T>(SessionFile file, string instructions, CancellationToken cancellationToken = default);
}
```

A reading that fails throws `DocumentReadException` with its reason, as a render that fails throws
`PageRenderException`, and the tool turns it into the text the model reads (ADR 0005).

This child changes two things from the parent's picture, and both follow what the repository does today. A file
is found by its name and has no id of its own, because a session's attachments are kept by name already and a
second key would be a second thing to keep in step. And the reader gives back the record or throws with the
reason, where the parent drew a record that might be null, because a null says nothing about why.

### 2. Where each part goes

![The wire carries the bytes, the API keeps them, the contracts say what a pack may ask, and the engine's reader calls the model and writes the ledger](diagrams/F171.1-a-photo-or-a-pdf-reaches-a-tool-architecture.svg)

The bytes travel inside the message's JSON as base64, the way the admin's price import already sends a file
(`ImportFileBody`, with its content as a `byte[]`), so the API needs no form and no second endpoint. An attachment that carries bytes is a
file, and one that carries text is what it is today.

The API checks a file before it keeps it. Its type must be one of the five the enum names, and it may weigh at
most 10 MB, which is Claude's own limit for an image. A session keeps at most 20 MB of files, the import's
number. A file that fails a check is refused with a 400 that says which check. The bytes live in memory with the
session, as its history does, and are never written to a log or to disk.

The model that runs the conversation never gets the bytes. It reads one line that says a file is attached, with
its name, type and size, and a tool can then be given that name. That keeps the conversation small and keeps the
photo out of every later request of the chat.

### 3. The main case

![The photo travels as bytes and stays with the session, the conversation's model sees only its name, and the reader makes one model call and writes one ledger row](diagrams/F171.1-a-photo-or-a-pdf-reaches-a-tool-communication-a-tool-reads-an-upload.svg)

The tool in the picture is a made-up one in the tests, `ReadSample`, with a made-up record. The first real one is
the bills pack's, in F171.2.

The host builds one pack context for all its sessions, so the context can't hold one session's files. It reaches
them the way an asked agent reaches the session's text attachments today: the API sets them for the turn, and the
context reads what is set (`SessionAttachments` is the code to copy).

### 6. What is reused

No new package. `DataContent` and `GetResponseAsync<T>` come with Microsoft.Extensions.AI, which the engine is
built on (ADR 0002). The reader's model client is stacked as the summaries' client is, traced, replayed and
recorded, and its ledger row is written by `UsageRecordingChatClient` under a `UsageScope`, as a summary's is. The
turn's files copy `SessionAttachments`. The bytes in JSON copy the import. The members that say no copy
`NoSitePlaces`. The media type is an enum read once with `SettingChoice.TryParse` and written with `.Wire()`
(ADR 0024). The setting that names the reading model is read by the loader that reads `MINION_LLMS`. The refusals
and the line the model reads are message enums with holes records (ADR 0009).

### 7. What this child leaves out

The web chat's composer still attaches text only, since the phone app's own composer is F171.6's. A file is not
handed on to an agent asked on another instance. Nothing is stored past the session: keeping a bill with an
account is F171.5's. The Files API, which would upload a file once and name it in later requests, is not used,
because one reading sends a file once.

## Steps

Each step is one commit with its test, written first and seen failing on an assertion. Stop after each for
Louis's review. A step that meets a choice this plan does not settle stops and puts it to him.

### Step 1: the plan is kept

A docs-only step, so it has no test first. It commits this plan and its pictures, as JSON and SVG together, its
row in the plans' index, and F171.1 marked as started in the TODO's and the work log's F171 rows. If Louis says
yes to the new line for ADR 0028 (under *Verification*), it goes in here with its line in the design rules.

Checked by `dotnet test src/tests/tools/LouisAgent.DocDiagrams.Tests` and the Docs tests in `LouisAgent.Core.Tests`.

### Step 2: the adapter is proved

This step proves what the rest stands on, before anything is built on it. The test is live and costs well under
a US cent: it builds the Anthropic client as a host does, sends a made-up account as a JPEG and then as a PDF
with a small record's schema, and asserts the record comes back with the account number and the amount on the
page. It is marked as an integration test and skips, saying so, where no key is set. The two sample files are
drawn for the test and show no real person or account.

There is no code to write after it, so this is the one step whose test is not seen failing first. If either
reading fails, the plan stops here and the ways on go to Louis as a finding: Haiku 5.5 may need another model for
PDFs, or the adapter may need the provider's own client behind a strategy (ADR 0003).

Run the one test with a key, and report what it cost.

### Step 3: an attachment carries bytes

The test comes first, as new cases in `SessionRequestJsonTests`: a message whose attachment has bytes and a media
type is read from JSON with its bytes whole, and written back the same, and a message with a text attachment
reads exactly as it does today.

Then the code. `AttachmentRequest` gains two optional last members, `byte[]? Bytes = null` and
`string? MediaType = null`, so every caller written today still compiles.

Run `LouisAgent.SessionStream.Tests`, and the API's tests since they send messages.

### Step 4: what a pack may ask

The tests come first, in `PackContextFilesTests`. A pack context that says nothing of files finds none and
forgets without complaint. Its reader throws `DocumentReadException` with a reason that says this host has no
model to read with. `FileMediaType` reads `image/jpeg`, `image/png`, `image/gif`, `image/webp` and
`application/pdf`, writes each back the same, and takes no other word.

Then the code: the types of the map's step 4, and the two members on `IPackContext` with defaults, as `Places`
has one.

Run `LouisAgent.Core.Tests`, since a folder is added and the rule tests read it, and
`LouisAgent.Packs.Rules.Tests`, since `PackConvertibilityTests` holds the packs' shapes.

### Step 5: the session keeps a file

The tests come first, in `SessionFilesKeptTests`. A message with a JPEG of 1 MB is accepted and the session then
holds a file of that name, type and size. The same name again replaces it. A type that is not one of the five is
refused with a 400 that names the type. A file over 10 MB is refused with a 400 that names the limit, and so is
one that would take the session past 20 MB. A text attachment is kept as it is today.

Then the code. `AgentSession` keeps `SessionFile`s by name beside its text attachments, with the two limits as
named constants. `SessionHandlers.SendMessage` checks each attachment that carries bytes before the turn starts.
The refusals' words go in `ApiUserText`.

Before the code, read what the API allows a request to weigh. Nothing in the repository sets it, and a 10 MB file
is about 13.4 MB as base64. If the server's own limit is under that, it is put to Louis.

Run `LouisAgent.Api.Tests`.

### Step 6: a tool finds this turn's files, and the model is told the name

The tests come first. In core, inside a turn whose host set two files, the pack context finds each by name,
whatever the case of its letters, finds nothing for a name that isn't there, and no longer finds one it was told
to forget. Outside a turn it finds none. In the API, the prompt for a message with a file holds one line with the
file's name, type and size, and holds none of its bytes.

Then the code. `SessionFiles` holds the turn's files for the flow, as `SessionAttachments` holds the text ones.
`TurnAmbience` sets it. `TurnSessionFiles` is what `ToolsetContext.Files` gives. `TurnPrompt` writes the line from
`ApiModelText.AttachedFile`.

Run `LouisAgent.Core.Tests` and `LouisAgent.Api.Tests`. The line is new text the model reads, so regenerate the
golden files it touches.

### Step 7: the reader

The tests come first, in `ModelDocumentReaderTests`, over a model client made for the test. The request it gets
holds the instructions, the file as `DataContent` with the file's media type, and a response format that is the
record's schema. The JSON it answers comes back as the record. The ledger gets one row whose purpose is
`reading`. An answer that doesn't fit the schema, an empty answer and a failure from the provider each throw
`DocumentReadException` with the reason, and a cancelled call stays a cancellation.

Then the code. `ModelDocumentReader` takes a model client and makes the one call under
`UsageScope.Begin(UsagePurpose.Reading)`. `AgentEngineFactory` gives the pack context a reader over the
instance's model, stacked as the summaries' client is. The reader's summary names the pick: a reader the engine
offers, chosen over the whole model client and over a pack's own model (Louis, 2026-11-22).

Run `LouisAgent.Core.Tests`.

### Step 8: a reading replays

An eval replays a recorded run without paying for it, so a reading must be found again by what was asked. The
test comes first, in `ReadingReplayTests`: a reading recorded once is answered from the recording the second
time, and the same instructions with one byte of the file changed is a miss.

A recording's key is built from each message's contents, so this may pass as written. If it does, the commit is
the test alone, and says so. If the key leaves the bytes or the schema out, the fix is here.

Run `LouisAgent.Core.Tests`.

### Step 9: a setting names the model that reads

Louis's pick of 2026-11-22: a setting names the model that reads. It is Fowler's Plugin, "Links classes during
configuration rather than compilation", on the loader the minions' models already use.

The tests come first. With `READER_LLM` unset or `instance`, the reader uses the instance's own model. With it
set to a profile in `LLM_SESSION_PROFILES`, the reader's request goes to that profile's client and its ledger row
names that profile's model. With a name that is neither, the host refuses to start and says which names it has.

Then the code: the setting on `AgentOptions`, its check in `SessionLlmLoader` beside the minions', and the
factory's choice of client. The setting goes in each `.env.example` and in `SETUP.md` and `MODELS.md`.

Run `LouisAgent.Core.Tests`.

### Step 10: the whole path, and the close

The test comes first, live, in the API's integration tests: a session on a host whose catalogue has the made-up
`ReadSample` tool is sent the sample JPEG, then the sample PDF, and each time the answer holds the account number
from the page and the ledger has a `reading` row with a cost. It skips, saying so, without a key.

Then the close, with `/finish-a-feature`: the design docs of the projects this child touched
(`LouisAgent.Core`, `LouisAgent.Api`, `LouisAgent.Core.Anthropic`) and their pictures, the how-to for a pack
author in the guides, the skill map's row 19, the write-up, the records, and this plan deleted.

## Verification

Every step's tests are named in it. Before the pull request, `main` is merged in and the full suite runs in the
pull request's checks, with Core's rule tests run here first. The live readings are four in all, in steps 2 and
10, each well under a US cent on Haiku 5.5. They are test calls, so they run without asking and their cost is
reported after.

**Done when:** a test sends a JPEG and a PDF through the real adapter and gets a typed record back, and a usage
row has the reading's cost. That is the parent's done-when for this child.

**For Louis's yes: one new line in ADR 0028.** A reader on the pack context is a second thing a pack's tool takes
from the engine beside its parameters, so the ADR that keeps packs convertible to MCP should say so. Proposed: "A
pack's tool that needs a model to read a file takes the file's name as a parameter, finds it in the session's
files and asks the engine's reader on the pack context. It holds no model client and no key. Served as an MCP
server, with no engine behind it, the pack is given a reader that calls a provider itself, as MCP advises since
it deprecated sampling (SEP-2577)."

**After the merge.** The bills pack takes this from the framework's packages, so a new version of
`LouisAgent.Composition`, `LouisAgent.SessionStream`, `LouisAgent.Core` and `LouisAgent.Api` has to be tagged
(ADR 0130). The tags are Louis's to say.
