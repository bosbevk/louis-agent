## Context

F127 ("a site's areas in the framework") has its visitor area, the showroom (F127.1, F127.2, ADR 0115, ADR 0116) and
the agent-to-agent work (F127.3 to F127.5, ADR 0117) done. Left: "the chat portal, the admin portal; a site names the
areas it uses; an ADR". The two portals' frames already live in the framework: `ChatShell`
(`Components/Chat/Shell/`), which Puls, code-review and the starter fill, and `AdminShell`, `AdminFrame` and the
packs' data screens (`IDataScreen`, `PackViews`, `Pages/Admin/`). What is missing:

- **A site can't name its areas.** Each `Program.cs` wires them by hand (`ChatSettings`, `ChatStore`, `AgentApi`,
  `CurrencyState`, `ChatText`, `ChatHandoff`, `SiteFrames`, `AddLouisAgentAccounts()`, `AddLouisAgentEvals()`, a
  `PackViews` filled by each pack's `AddTo`), and each `App.razor` lists the page assemblies
  (`FrameworkPages.With(AccountLibrary.Assembly, EvalLibrary.Assembly)`). code-review and the starter repeat it near
  line for line.
- **code-review and the starter run the evals but never link them:** only Puls's admin layout draws `EvalLinks`.
- **No ADR** says what a site's area is.

## Design

### What changes, in plain words

- **One call names a site's areas:** `builder.Services.AddSiteAreas(areas => areas.Chat().Admin(...).Evals())`. Each
  area registers what it needs (its services, its frame, its pages), so a new site is a few lines and can't forget a
  part.
- **The libraries above the framework's web add their own area:** the eval studio's `.Evals()`, the accounts'
  `.Accounts()`. The framework's web names neither (dependencies point one way, ADR 0010).
- **The router and the admin frame read the areas:** the router's page assemblies come from them, and the admin frame
  draws each area's links, so every site that runs the evals links them.

### Interface design

![One builder, open from outside: the framework's web names three areas, the libraries above it add theirs](diagrams/F127.6-a-site-names-its-areas-interface.svg)

```csharp
// louis-agent.web, Components/Areas/ (step 2)
public static class SiteAreasServices
{
    public static IServiceCollection AddSiteAreas(this IServiceCollection services, Action<SiteAreasBuilder> build);
}
public sealed class SiteAreasBuilder
{
    public SiteAreasBuilder Chat(string? handoff = null);
    public SiteAreasBuilder Admin(Type layout, Action<PackViews>? views = null);
    public SiteAreasBuilder Showroom(ShowroomDemos demos);
    public SiteAreasBuilder Add(SiteArea area);
}
public sealed record SiteArea(string Name, Action<IServiceCollection> Services, IReadOnlyList<Assembly> Pages,
    Type? AdminLinks = null, Type? AccountLayout = null);
public sealed class SiteAreas
{
    public IReadOnlyList<string> Names { get; }
    public Assembly[] PageAssemblies { get; }
    public IReadOnlyList<Type> AdminLinks { get; }
}

// louis-agent.web.evals (step 3)
public static SiteAreasBuilder Evals(this SiteAreasBuilder areas, SiteKinds? kinds = null);
// louis-agent.web.accounts (step 3)
public static SiteAreasBuilder Accounts(this SiteAreasBuilder areas, Type layout);
```

A site's `Program.cs` then reads, code-review's:

```csharp
builder.Services.AddSiteAreas(areas => areas
    .Chat(handoff: "chat")
    .Admin(typeof(AdminLayout), views => { GitWebViews.AddTo(views); FilesWebViews.AddTo(views); })
    .Accounts(typeof(AccountLayout))
    .Evals());
```

and its router `AdditionalAssemblies="Areas.PageAssemblies"`.

## Steps

Each step test first, one commit, `core.tests` when a folder or a name is added.

1. **The plan**, its four pictures drawn.
2. **The builder** (`SiteAreasBuilder`, `SiteArea`, `SiteAreas`, `AddSiteAreas`) with `Chat`, `Admin` and
   `Showroom`. Tests: each area registers its services and page assemblies; an area named twice is refused.
3. **`.Evals()` and `.Accounts()`** in their libraries. Tests in their test projects.
4. **`AdminShell` draws the areas' admin links.** Tests: the evals link shows where the evals area is named, and not
   elsewhere.
5. **code-review on `AddSiteAreas`** (Program.cs, App.razor). Its route tests and goldens.
6. **The starter on `AddSiteAreas`**, and the template `dotnet new louis-site` makes. Its site tests.
7. **Puls on `AddSiteAreas`** (Puls follows framework changes while paused). Its route tests and the admin golden.
8. **louis-agent.dev on `AddSiteAreas`**, with `.Showroom(SiteDemos.All)`. The site's tests.
9. **A rule:** every site names its areas through the builder; no hand-registered `SiteFrames`, `PackViews` or
   `FrameworkPages.With` is left.
10. **The docs:** the ADR (a site names its areas; amends ADR 0084 and ADR 0111), the web's and the site's design
    docs, the spawn-a-site guide, the work log, the write-up, the full suite, this plan deleted.

## Verification

- **Each step:** the tests of what it touches; `core.tests` for new folders and names.
- **Steps 5 to 8:** each site run locally and looked at in Chrome (its chat, its admin pages, a screen, the eval
  links), at desktop and phone width, before the PR (Louis: "test local first").
- **Step 10:** the full suite, then one PR, merged only on green. No paid run: nothing here asks a model.
