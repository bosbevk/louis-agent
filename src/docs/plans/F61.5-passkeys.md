# F61.5 Passkeys and a second factor

> **Plan** (a child of [F61](F61-accounts-and-azure.md), which holds the design, the four diagrams and the namespace
> map). How a person adds a passkey (a fingerprint, a face, a security key) and signs in with it, and turns two-factor
> with an authenticator app on and off, both on Identity's own support. Started 2026-11-07 on
> `feature/F61.5-passkeys`, under the parent's approval of 2026-11-07. Deleted when the work is done.

## Done when

A person adds a passkey on the profile and signs in with it; two-factor with an authenticator app can be turned on
and off; both proved through the test host with a software authenticator, and by hand in a browser.

## Steps

The parent's *F61.5* section, one commit each, test first:

1. The schema: Identity's schema version 3 and the migration that makes the passkey table.
2. The routes: creation options and the new passkey, the list and delete, request options and the sign-in, under
   `/account/passkeys`; proved with a software authenticator the test writes (an ES256 key, a "none" attestation).
3. The pages: a passkey section on the profile and a "sign in with a passkey" button on the sign-in page, with the
   browser's `navigator.credentials` behind a small script of ours.
4. Two-factor: Identity's `/account/manage/2fa` with an authenticator app, the shared key and the `otpauth://` link,
   the QR code drawn by a class of ours, recovery codes; the sign-in form's second step.
5. Docs and the write-up.

## Approved during the build

Picks taken unattended (Louis, 2026-11-07: "do all unattended"), each the recommended one of three:

- **One migration, written again** (step 1). F61.1's migration was written with Identity's default schema, since
  the design-time factory gave the model builder no Identity options; version 3 shortens the key columns of the
  logins and tokens tables, and SQL Server refuses to alter a primary key's column. Options: a hand-written
  migration that drops and remakes the keys around the change; a second migration that leaves the long columns and
  adds only the passkey table (a schema that isn't Identity's); **delete the first migration and write one under
  version 3** (picked: nothing is sold and nothing is stored yet, ADR 0049; the factory now names the version).
- **A section, not a page** (step 3). The plan named a `PasskeyPage`; the profile already lists the other ways in
  (`LinkedLogins`), and a passkey is one more. Options: a page of its own at `/passkeys`, linked from the profile;
  **a `PasskeyList` section on the profile** beside the linked logins, with the sign-in button a `PasskeySignIn`
  component on the sign-in page (picked: one place for "how I sign in", no new route or words for a page title);
  a tab inside `LinkedLogins` (two concerns in one component). The browser's part is `passkeys.js`, three
  functions (`supported`, `create`, `get`) that pass Identity's JSON to `navigator.credentials` and the browser's
  `toJSON` back, untouched; a browser without the parsing helpers sees no form and a line saying so.

## Verification

`dotnet test src/tests/hosts/louis-agent.accounts.tests`, the accounts integration tests on the Docker SQL Server,
`src/tests/web/louis-agent.web.tests`. By hand, free: on the PC's Puls stack, add a passkey with Windows Hello, sign
out, sign in with it; turn two-factor on with an authenticator app, sign out, sign in with a code. No paid run.
