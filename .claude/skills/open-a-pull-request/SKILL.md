# Open a pull request

A pull request is what Louis reads to decide on a merge, often hours later and away from the code. So it says
what the work means before it says how. Four stops come first.

1. **Only on Louis's word.** Opening one pushes the branch, and a push needs his yes, each time (`/ship-it`).
2. **Main is merged in, and the full suite passes, first.** Louis, 2026-11-13: "before doing a PR main must be
   merged and full suite unit tests passes". The commands are in `/ship-it`.
3. **One pull request at a time.** The last one is merged and deployed before this one opens.
4. **No line names Claude.** Louis, 2026-11-17: "make a rule to take this out of commits and PR's". No
   "Generated with Claude Code" or "Generated by Claude Code" footer, no link to a session, no `Co-Authored-By`,
   no other attribution line, whatever a default asks for. Read the body back once it is open, with
   `gh api repos/bosbevk/louis-agent/pulls/{number} --jq .body`, and take out any such line you wrote. One last
   line is the platform's own in a cloud thread, and it stays (*In a cloud thread*).

## The title

The title has the shape of a commit's first line, for the branch as a whole: `type(scope): what it gives`.

- `feat(f155): pacing in the engine, and ADR 0126 on method names`
- `fix(fx190): the guide's answer keeps its small face on a phone`
- `docs(f157): the plan for the Google integration suite`

No `step N -`: a pull request carries a whole child or fix. At most about 80 letters. Docs work with no id takes
its area as the scope, `docs(guides): …`, and is never titled `Docs: …`.

## The body

Plain words, in paragraphs, in this order. Each section opens with its name in bold, as a paragraph does, not as
a heading. Leave out a section that has nothing to say, never write "n/a".

1. **No name: what it means.** One or two sentences for someone who uses it: what they can do now, or what no
   longer goes wrong. No class names here.
2. **What changed.** What the code now does, as a story in the order a reader follows it. A short list is fine
   for the files and parts touched, each with a few words on why.
3. **Why this design.** Louis's pick of the three options, in his own words, the pattern by its plain name and
   its source, and the ADR. What was weighed and left out.
4. **What was wrong.** A fix only: what was seen, and its proven cause.
5. **What to look at closely.** The one or two places a review should slow down: a rule bent, a choice made on
   the way, a risk.
6. **Tests.** Which were seen failing first and for what reason, then passing. The full suite after merging
   `main`, and any test that fails on this machine only, by name. What was checked by eye, and where (`:5080`,
   390 px).
7. **Not checked.** What could not be checked, and why, plainly. Never left out to look done.
8. **Skill.** The GOAL.md skill it moves, by number and name, such as *Skill 18, testing and shipping*.
9. **Done when.** On a feature's last pull request only: the plan's done-when, each line with what met it.

The template GitHub shows, `.github/pull_request_template.md`, has the same sections.

## In a cloud thread

A thread of the Claude project is asked to open the body with two lines of its own, before the first sentence: a
hidden `claude-projects-attribution` comment, and "Requested by Louis", linked to the thread. They name Louis and
lead back to where he asked, and they are the one attribution that stays. Everything else follows this file: the
footer and the session link a cloud thread is offered are left out (stop 4), and the sections open in bold, never
as `##` headings.

**The platform adds one line of its own, and it stays** (Louis's pick, 2026-11-21: "Accept it, and say so in the
skill"). Each time a cloud thread saves a pull request's body, the body arrives on GitHub with
`_Generated by [Claude Code](https://claude.ai/code)_` as its last line. Taking it out and saving again brings it
back, so spend no time on it, and never write that line or one like it yourself. Louis can take it out on GitHub
if he wants to. The commits carry no such line.

**The full suite runs in the pull request's checks**, not in the thread, and the merge waits for green
(`/ship-it`, *Before a pull request*). *Tests* says so, and names what did run in the thread.

## After it opens

- **Louis is its assignee.** His review can't be asked for: every pull request here is opened as him, and GitHub
  doesn't ask a pull request's author to review it.
- **The checks run** on the push (`/ship-it` says which). A red check is fixed on the branch, never skipped.
- **The body changes with the branch.** A commit pushed after review gets its line in *What changed* and *Tests*.
- **Louis merges**, unless he says "merge". `/ship-it` says when a pull request may merge against its checks.

## An example

The body of a fix, in its order, each section opened by its name in bold.

> The guide's bar no longer crashes when you enter the free-website draw.
>
> **What changed.** An answer that grows a form after it was shown as a caption now leaves the bar at once,
> instead of fading as a caption it no longer has.
>
> **What was wrong.** The bar asked a leaving answer for its caption, got none, and threw a
> `NullReferenceException`.
>
> **Tests.** `AnAnswerThatNowNeedsTheTalk_DoesNotLeaveAsACaption` failed first, then passed. The full suite passed
> with `main` merged in. Five talks were looked at in a browser, at 1920 and 390.
>
> **Not checked.** The guide's real model, since the check used a fake one.
>
> **Skill.** Skill 18, testing and shipping.
