## Context

**What Louis asked:** the guide runs a business's demo live for a visitor: it asks the business on the server in the
visitor's own words, the page shows that talk in the business's own window, and the visitor carries on there in the
same session (F127.3 pick 7, L2: "the guide asks on the server, the page shows it in the business's window, and the
visitor carries on in the same session"; 8, C2: "the window shows the talk, the card shows the work"). The door counts
that session as one of the visitor's (F127.4 pick 7), the guide learns what the business did from each tool's own
result line (6), and follows what the visitor typed in the window with `ReadAgentWork` when it needs to (8).

**What exists:** `AskAgent` asks a business on this instance through the API's own sessions and streams its events,
nested as `sub_session`, into the guide's turn (F127.3.1); the nested `message_start` already carries the business's
session id; the guide's widget hides its work; a showroom's live window (`MockLiveChat`) opens its own session through
the open door; `GuideDoor` lets any button reach the widget (an Observer); the cards an agent draws work in both
chats (F127.4.1). Missing: the window can't take over a session someone else opened, the door doesn't know an asked
session belongs to a visitor, `ReadAgentWork` sees only what streamed through the guide's own asks, and the did line
names tools without what they gave back.

## Design

### What changes, in plain words

- **The did line says what each tool gave back** (pick 6): "ShowPage: shown /rooms/garden · ShowCard: shown · Offer:
  offered 3 choices", each call's first line, cut short, so the guide retells it right without reading the stream.
- **A session's work over the API**: `GET /v1/sessions/{id}/work` gives a session's steps (what it said, each call
  with its input and what came back, without its thinking) as records; the door lets an admitted session's own work
  through.
- **`ReadAgentWork` reads the asked session's whole work** from its server, so the turns the visitor typed in the
  window count too (pick 8).
- **The door admits an asked business's session for the visitor who asked** (pick 7): a session opened with an
  admitted session as its parent is admitted too and counts as one more of that visitor's sessions that day; over the
  cap, the ask is refused with the reason, which the guide passes on.
- **The page routes the talk into the window** (C2): the web learns each asked agent's session id from its nested
  `message_start`; `AgentWindows`, a small shared object like `GuideDoor`, lets a page's live window say which
  identity it shows; when the guide's turn holds an `AskAgent` call to that identity, the window shows the ask as the
  visitor's message and the business's answer live, its page moves and its cards draw.
- **The visitor carries on in the window** (L2): the window takes the asked session as its own, so the next message,
  typed or a card's click, goes to the same session; the guide's next ask goes there too.
- **The guide**: offers the live demo at *What to watch* with `Offer` (watch it live, try it yourself, just the
  recording), asks the business in the visitor's own words (pick 1), says in a line that the business answers in its
  window, and coaches after, reading the work when the visitor asks what happened.

## Steps

Each step test first, one commit, `core.tests` when a folder or a name is added.

1. **The plan**, its pictures drawn.
2. **The did line with each tool's result** (pick 6): `AgentWork.ToolCall` keeps the first line of what came back,
   cut at 80 characters; `DidLine` writes `Tool: result` for each call. Tests: `DidLineTests`; the model goldens.
3. **A session's work over the API**: the records in `session-stream`, `GET /v1/sessions/{id}/work` built from the
   session's history (said, called, came back, failed; no thinking), 404 for an unknown session, the door passing an
   admitted session's own call. Tests: the API's session tests, a contract test.
4. **`ReadAgentWork` reads the whole session** from its server through `PeerSession`, falling back to what streamed
   when the server can't be reached. Tests: with a stub server, a turn the guide never saw is read.
5. **The door admits an asked session** for the visitor whose session asked, counting it that day; over the cap the
   ask is refused with the reason. Tests: `OpenDoorTests`, a session handler test.
6. **The web learns the asked session and routes it**: `Block.SubSessionId` from the nested `message_start`;
   `AgentWindows` (an Observer, registered by a site); the widget raises `Asked` for an `AskAgent` block whose address
   is an identity a window shows. Tests: `TurnStreamTests`, `AgentWindowsTests`.
7. **The window shows the talk and carries on**: on `Asked`, `MockLiveChat` opens live, shows the ask as the
   visitor's message and folds the business's events as its answer as they stream, then takes the session
   (`ChatRunner.Adopt(sessionId, turn)`), so the next message goes there. Tests: bUnit on `MockLiveChat`,
   `ChatRunnerTests`.
8. **The guide's side and the prompts**: a windowed ask shows one line in the guide's chat ("Seemeeu Guesthouse
   answers in its window"); the guide's voice offers the live demo at *What to watch*, asks in the visitor's words and
   coaches with `ReadAgentWork`. Tests: bUnit, `LouisVoiceTests`; the goldens regenerated.
9. **The live check** on the PC, desktop and 390 px: the guide runs Seemeeu's demo, the visitor books in the window
   with a card, the guide retells it right; the mail key blanked; the cost reported.
10. **The docs**: the design docs of core's delegation, the API, the web and the site's guide (their pictures), ADR
    0117's record if the door's rule changes it, the work log, the write-up, the full suite, this plan deleted.

## Concepts, and where they sit in GOAL.md

- **Multi-agent orchestration** (skill 10): one agent asks another for a person and hands the conversation over.
- **Human in the loop** (skill 16): the visitor takes the wheel in the business's window; nothing is sent before their click.
- **Observability** (skill 17): the did line and a session's work make what an agent did readable by another.
- **Safety** (skill 15): the door counts a session an agent opened for a visitor as theirs, under the same cap.

## Claude's picks (unattended), each of three

| # | Question | Pick | The other two |
|---|---|---|---|
| Q1 | How the window learns the asked session | **From the nested `message_start`, already in the stream** | A session id on every `sub_session` event: a wire change for what is there · The tool's text names it: the web parses words |
| Q2 | How the widget reaches the window | **`AgentWindows`, a shared Observer like `GuideDoor`** | Script events between the two: a second channel beside Blazor's · The showroom page owns both and passes parameters: the corner widget belongs to the layout, out of its reach |
| Q3 | How the visitor's typed turns reach the guide | **A session's work over the API, which `ReadAgentWork` reads** | The page tells the guide in the next message's page block: words the model reads every turn · Not at all: pick 8 says the guide follows them |
| Q4 | The door and an asked session | **Admitted when its parent was, counted in that visitor's day** | Every child of an open identity admitted uncounted: a way round the cap · The window opens its own session and replays the talk: not the same session (L2) |
| Q5 | What the guide's chat shows while the business works | **One line: it answers in its window** | Nothing, as with the work hidden: the visitor looks for an answer · The whole delegation card: the talk twice on one screen |
| Q6 | How long a result runs in the did line | **Its first line, cut at 80 characters** | The whole result: long tool texts flood the guide's context · Only failures: pick 6 says each tool's result |

## Approved during the build

- **No new runner method** (step 7): a runner's `Chat` is settable, so the window takes the asked session through
  `WatchedAsk`, which builds the chat; the plan's `ChatRunner.Adopt` was not needed.
- **The live check** (step 9, on the PC, the mail key blanked): the guide asked the guesthouse in the visitor's words,
  the stage went live with that talk, the visitor carried on there (a card's click and typed details, the ticket and
  *Book it*), the website moved to the garden room, and the guide retold it all from `ReadAgentWork`, the window's
  turns included. US$0.0234 for the day's live checks to that point.
- **On a phone the guide folds** (step 9, the 390 px check: the guide's panel covered the business's window). Of
  three (always fold, which hides the guide's line on a wide screen where the stage shows anyway; only say so, which
  leaves the visitor to find the window behind the panel), Claude's pick: **on a narrow screen the module brings the
  window into view and the guide folds to its head** (`showWindow`).
