# F126.3.1 Runs

A plan: how an eval file is run against a live agent, how the run is graded, kept and followed, and how the same
run is replayed for free. It is the first of the two children of F126.3, *runs and the run page*, in
[F126 Evals, redesigned](F126-evals-redesigned.md), which says what was decided and why. This file says what this
child builds, then gives its eleven steps. It builds no page: the screens are F126.3.2's.

![Five parts: a conversation is played over the sessions API and graded, repeats decide a pass, a run is kept as one file, a site's API starts and follows a run, and a replay costs nothing](diagrams/F126.3.1-runs-overview.svg)

## Design

### 1. A run, in plain words

A run takes one eval file and plays every conversation in it against the agent the file names, through the same
sessions API a person's chat uses. Each conversation gets a session of its own. The run sends the first turn's
ask, reads the answer as it streams, and writes down what happened as a transcript. Then it sends the next turn
in the same session, since a follow-up only means something when the agent remembers. When the conversation is
over the session is closed, code tells each turn's facts, and the judge marks each turn's criteria.

A run asks for one repeat or three. With three, the whole conversation is played three times, each in a fresh
session, because a model doesn't answer the same way twice. A conversation passes only when every fact and every
criterion of every turn is met in every repeat. The run's number is how many conversations passed.

After each conversation the run is written to its file again. So the file is the progress, and whoever wants to
know how a run goes reads the same file a finished run is read from.

### 2. The records of a run

A run is a small tree, and the tree is what is kept, what the API sends, and what F126.3.2's pages will draw.

![A run holds its conversations, a conversation its repeats, a repeat its turns, and a turn its transcript and its marks; the player, the runner and the store are the three classes that make and keep it](diagrams/F126.3.1-runs-interface-design.svg)

```csharp
public sealed record EvalRun(
    string Id, string Eval, string Agent, RunKind Kind, int Repeats, DateTimeOffset StartedAt,
    IReadOnlyList<ConversationRun> Conversations)
{
    public RunStatus Status { get; init; } = RunStatus.Running;
    public DateTimeOffset? EndedAt { get; init; }
    public string? StoppedBecause { get; init; }
    public bool PageSent { get; init; }
    public int Passed { get; }
}

public sealed record ConversationRun(string Id, IReadOnlyList<RepeatRun> Repeats)
{
    public bool Passed { get; }
}

public sealed record RepeatRun(int Number, IReadOnlyList<TurnRun> Turns)
{
    public bool Passed { get; }
}

public sealed record TurnRun(
    TurnTranscript Transcript, IReadOnlyList<Mark> Facts, IReadOnlyList<Mark> Criteria,
    decimal? Cost, string? Currency);

public enum RunKind { Live, Replay }

public enum RunStatus { Running, Finished, CouldNotFinish }
```

They live in a new small project, `LouisAgent.Evals.Contracts`, because the pages run in the browser and a
browser project can't reference `LouisAgent.Evals`, which stands on the engine. `Mark`, `TurnTranscript` and
`ToolCallTranscript` move there from `LouisAgent.Evals`, where F126.2 put them. The pattern is the shared contract
the API and the accounts already have (ADR 0045): one shape both sides compile against, so a renamed field breaks
its readers at build time.

Whether something passed is asked of the record and never worked out where it is shown (ADR 0123). A repeat passed
when every mark of every turn is met. A conversation passed when it has every repeat the run asked for and each
passed. A cost nobody could price is null, never 0 (ADR 0007). Dates are UTC (ADR 0046).

`PageSent` is false on every run of this child. It is on the record so a run says plainly that the agent was
asked without the page a visitor's message would carry.

### 3. A turn is asked, and written down

The session client comes back from git, cut down to what a run needs: open a session, send a message and read its
events, close the session. It is one class over an `HttpClient`, with no interface: a test gives the client a
handler that answers, so nothing needs a second implementation.

A transcript is filled from the stream's events. Text deltas join into the answer as the agent sent it. A tool
call is its name and its input, and its result is the result block whole, with whether it failed. An `error`
event is the turn's error. The turn's last numbers carry its cost. The events of an agent that was asked
(`sub_session`) are that agent's own work and stay out of this turn's calls: the call to `AskAgent` is already
one of them, with the answer as its result, and that is what the two facts about another agent read.

### 4. Playing a conversation, and grading it

![One conversation of a live run: a session is opened, each turn is asked and written down, the session is closed, code tells the facts, the judge marks the criteria, and the run's file is written again](diagrams/F126.3.1-runs-communication-one-conversation-of-a-live-run.svg)

```csharp
public sealed class ConversationPlayer(SessionClient sessions, Judge judge)
{
    public Task<RepeatRun> PlayAsync(
        AgentAddress agent, Conversation conversation, RunTrial trial, CancellationToken cancellationToken = default);
}

public sealed class EvalRunner(ConversationPlayer player)
{
    public Task<EvalRun> RunAsync(
        EvalRun started, EvalFile file, Func<EvalRun, Task> kept, CancellationToken cancellationToken = default);
}
```

The player plays one conversation once. The session opens as the file's agent: the address's identity, and its
role when it names one. It always closes the session, also when a turn failed. A turn that ends in the agent's
own error is still a turn: its transcript holds the error, `no-error` is then not met, and the conversation goes
on to its marks. That is the agent failing, which is what an eval is for.

The runner plays every conversation as many times as the run asks, hands the run to `kept` after each
conversation, and ends it as finished. Two things end it as could not finish, with the reason in
`StoppedBecause`: the API refusing or dropping the session, and the judge not being able to mark
(`JudgeFailedException`). In both, nothing was learnt about the agent, so no mark is made up. Everything graded
before the stop is in the file.

The pattern is a pipeline, a conversation in and a graded repeat out, as the parent names it. The two classes are
split by what changes them: the player knows the sessions API, the runner knows repeats and stopping.

### 5. A run is kept as one file

```csharp
public sealed class RunStore(string folder)
{
    public void Save(EvalRun run);
    public EvalRun? Find(string id);
    public IReadOnlyList<EvalRun> Of(string eval);
}
```

One JSON file per run, in `evals/runs/` under the site's data folder, named by the run's id. The id is the UTC
time the run started and the eval's name, `20261123-043012-guide`, so a folder listing is already in order and a
person can open a run in Rider. A file is written beside itself and moved into place, as the CV's is, so a reader
never meets half a run. An id is checked before it is part of a path (ADR 0004). The reader is strict, as every
reader of ours is.

The pattern is Fowler's Repository: the endpoints ask the store for runs and don't know they are files. A host
with no data folder has nowhere to keep a run, and the start of a run is refused with that reason.

A run that was cut off by a restart is still in its file with the status running. Only one run runs at a time,
and the part that runs it knows which. So a stored run that says running and isn't that one is read as could not
finish. No clean-up job is needed.

### 6. Eval files are found like prompts

An eval file sits in its agent's folder, `agents/{identity}/{name}.eval.json`, and the identity's project embeds
it with one more line in its project file. The catalogue already hands over every identity's and pack's embedded
files for the prompt reader, and that reader takes only `.md` files. So an eval file travels the same way and no
prompt ever sees it. `EvalCatalog` walks those providers once at start-up, reads every file whose name ends in
`.eval.json` with F126.2's reader, and holds them by name.

The eval's name is the file's name without its ending, `guide`. A wrong file, two files with one name, or a file
whose agent this host doesn't have stops the host at start-up with the reason, as a missing role does today. The
guide gets its first file here with one conversation, `guide-what-is`, so there is something real to run. F126.5
writes the evals proper.

### 7. Starting a run, and following it

![The eval library is mapped by the site's own API program; a run asks the agent over the sessions API, keeps its file in the data folder and its recordings in the replay folder](diagrams/F126.3.1-runs-architecture.svg)

The eval part is a library, `LouisAgent.Api.Evals`, that a site's API program maps with one line, on the API's
own group and behind the admin key. Four routes:

| Route | What it answers |
|---|---|
| `GET /v1/admin/evals` | Every eval this host has: its name, its agent, how many conversations, and its last run in short |
| `POST /v1/admin/evals/{name}/runs` | Starts a run. The body says live or replay, and one repeat or three. `202` with the run's address in `Location` |
| `GET /v1/admin/evals/runs/{id}` | The run as it is kept, running or ended |
| `GET /v1/admin/evals/{name}/runs` | That eval's runs in short, the newest first |

A start is refused with its reason before anything runs: an eval this host doesn't have is a `404`, a run already
going is a `409`, and repeats that are neither 1 nor 3, a host with nowhere to keep a run, or a replay with no
live run to replay are each a `400`.

The run then goes on in the background of the same process, and the request that started it has long been
answered. This is Microsoft's Asynchronous Request-Reply pattern with one thing left out: their status address
redirects when the work is done, and ours keeps answering the run, since running and ended are the same record.

The run reaches the agent the way any app does, over HTTP, at the program's own address, with the instance's own
key. So the engine and `LouisAgent.Api` hold no eval code, and the agent that is measured is the one visitors
get.

A live run spends money, and Louis's rule is that it waits for his go. In this child there is no page, so a live
run starts only when someone with the admin key calls the route by hand. The ask with its estimate is F126.3.2's.

### 8. Record and replay

![One run in memory: the run holds its conversations, each its repeats, each its turns with a transcript and marks, and beside it the trial's recordings](diagrams/F126.3.1-runs-objects-in-memory.svg)

A live run records as it goes. Each repeat's session opens with a run tag, the run's id, and asks the API to
record, so the engine saves the model's and the web's answers under the trial `{run id}/{conversation}.{repeat}`.
That is existing behaviour, asked for with two fields of the session's request.

The judge is a model call too, but it runs in the eval library and not in a session, so nothing records it
today. The run wraps the judge's client in the engine's own replay client and marks each conversation inside the
same trial. So a trial holds the agent's answers and the judge's.

A replay finds the eval's last live run that finished, and plays the same conversations with each session asking
for that run's trial back, model included. Nothing calls a model, so it costs nothing. The result is a run like
any other, kept in its own file with the kind replay.

A recording answers only the request it was made from. When a prompt, a doc the agent reads or a criterion's
words have changed since, the recording holds no answer: the agent's turn ends with `replay_miss_error`, or the
judge can't mark. Either way the replay stops and says the recording is out of date and a live run is needed. It
is Fowler's self-initializing fake, which makes no attempt to know when its recording went stale; here the miss
is how we find out. Marking only the reworded criteria live is F126.4's re-grade.

The same replay is one test. A helper plays an eval from recordings kept in git and checks its facts only, with
no model and no key, and fails on a fact that isn't met or a recording that is missing. The guide's recordings
sit in `src/site/recordings/evals/`. So a pull request that changes the guide's prompt turns that test red until
a live run records again, on Louis's go. That is the gate seeing the agent changed.

### 11. What is reused

No new package. The stream is read with `SessionStreamReader` and the session's requests and replies are the
shared wire records (`CreateSessionRequest`, `SendMessageRequest`, `ReplayRequest`, `SessionCreatedReply`), so
nothing of the wire is typed twice. The client's shape is the old `HttpSessionClient` from git. Recording and
replay are the engine's: `ReplayStore`, `ModelReplayChatClient`, `SessionReplay`. The judge's cost lands on the
ledger through the engine's `UsageRecordingChatClient`, under the `grading` purpose F126.2 already sets. The
routes sit on `MapLouisAgentHostGroup` and `MapAdminGroup`, as the CV's do, and answer with the API's own error
shape (`ApiErrors`). The store writes a file the way `ResumeStore` does. Eval files come through
`AgentCatalog.Prompts`. The tests use `FakeChatClient` and the API on a test server, as `ApiTestHost` builds it.

### 12. The small calls this plan makes

These were too small for a card. They are listed so that approving the plan approves them, and any of them can be
changed with a word.

| The call | Why |
|---|---|
| The judge marks after the conversation is over, not after each turn | One place opens and closes the session, and the judge reads the turns either way |
| An agent's own failure in a turn is graded, and a failure to reach the agent stops the run | The first is the agent's result. The second says nothing about the agent |
| The eval's name is its file's name, one per host, and a wrong file stops the host at start-up | The reader's pick was to stop at the first fault, and a role file does the same today |
| A run's id is its start time and the eval's name | A folder listing is in order with no index, and the id is safe in a path |
| The judge's model is a setting, `EVALS_JUDGE_MODEL`, and the host's own model without it | A site says which model judges without a rebuild |
| The run reaches the agent at `EVALS_API_URL`, the program's own address without it | The agent is asked like any app, and a test points it at a test server |
| A live run needs the host to keep recordings (`REPLAY_DIRECTORY`), or its start is refused | Every live run can then be replayed, with no second kind of live run |
| In a replay `under {seconds}s` is told from the replay's own time | The recording holds no timings. The run's kind says so, and the fact means little there |
| The guide's file holds one conversation here | Enough to prove a run. F126.5 writes the evals |
| `LouisAgent.Evals.Contracts` and `LouisAgent.Api.Evals` are not packages yet | A project is a package only by saying so (ADR 0130), and no product outside this repository runs an eval before F171.4 |
| The leftover MongoDB package line in `LouisAgent.Api.csproj` is not touched | It is not this child's, and removing a package from the API wants its own look |

### 13. What this child leaves out

The screens, their four states and the ask before a live run are F126.3.2's. The page a conversation names is
F126.3.3's, planned before F126.5 writes the guide's evals, and until then a run says it sent none. Flips,

shows costs: here it is on the ledger under `grading`, and the run carries what the agent's turns cost.

## Verification

Every step's tests are named in it. Before the pull request, `main` is merged in and the full suite runs in the
pull request's checks, with Core's rule tests run here first. The paid calls are step 10's one live run of one
conversation three times, on Haiku 5.5 at $0.10 for a million tokens in and $0.50 out
([pricing](https://platform.claude.com/docs/en/about-claude/pricing)), which should be a few US cents; it is a
test call, so it runs without asking and its cost is reported after. Free and by hand: the replay of that run,
and the run's file read in Rider.

**Done when:** the guide's eval is started through the site's API and ends as a run kept in one file, with each
turn's transcript and marks; with three repeats a conversation passes only when all three do; a run that can't
go on ends as could not finish with its reason and keeps what it graded; a replay of that run ends with the same
marks and calls no model; and one test replays the guide's eval from recordings in git with no key. No page
exists yet.

**Two new lines in ADR 0134, with Louis's yes.** Two of this child's picks are rules a later change must follow,
and one of them changes what the parent plan said, so the ADR that says what an eval is should hold them: "A run
is kept as one file in the site's data folder, behind a repository, and what is kept is what the API sends and
the page draws. A live run records as it goes, the judge's answers too, so a replay is a whole run that costs
nothing, and a recording that no longer answers stops the replay." They go into the ADR in step 11, with the
close. Louis said yes to them when he approved this plan, on 2026-11-23.
