## Context

Louis, 2026-11-12: "each projecs doc needs an interface diagram", then "so each project has a
architecture/flow/seq/interface diagrams". There are 42 project docs: 25 in `src/docs/projects/`, 9 in
`packs/docs/projects/` and 8 in the demos'. Every one opens with its overview (the project and its parts, CL60.1).
34 also show a flow of how it works with its neighbours and 29 a sequence of a main case (CL60.2, CL60.3). None
shows its types. So the gap is 42 interface pictures, 8 flows and 13 sequences, each written from the project's
own code.

## Design

### What changes, in plain words

- **Every project doc shows four kinds of picture:** its overview (cards: the project and its parts, which is its
  architecture), a flow (how it works, from who calls it to what it reaches), a sequence (its main case, call by
  call) and its interface design (a `classes` picture of the types someone using or extending it meets).
- **The interface picture is drawn from the code:** the public interfaces, records and main classes, at most about
  twelve, with the members a caller uses, and what implements, holds and creates what. It goes in the doc's
  `## Diagrams` section, which a doc without one gains above its *Structure*.
- **A test holds it:** `EveryProjectDoc_ShowsItsFourDiagrams` reads the kind of every picture a project doc links
  and wants all four. Until the last step the docs still to do are listed in a pending list that only shrinks: a doc
  not on it must have all four, and a doc on it that has them fails too, so its name comes off in the step that
  draws its pictures.
