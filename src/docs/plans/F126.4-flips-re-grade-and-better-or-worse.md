# F126.4 Flips, re-grade and better or worse

A plan: how a person corrects the judge, grades a run again after changing the eval file, and sees whether the agent
got better or worse. It is the fourth child of [F126 Evals, redesigned](F126-evals-redesigned.md), which says what
was decided and why. This file says what this child builds, then gives its thirteen steps.

**Why it matters.** The judge is a model, and it is sometimes wrong. Until a person can say so, a run's number
mixes the agent's mistakes with the judge's, and nobody can tell which criterion to reword. And once a criterion
is reworded, today's only way to see what that does is a paid live run. A run also says nothing about the run
before it, so a person can't see at a glance whether a change made the agent better or worse.

**What the code has, on `main` at `12a7fe72`.** A mark is a record of three things, `Mark(Text, Met, Reason)`: the
fact's words or the criterion, met or not, and why. A repeat passes when every mark of every turn is met
(`RepeatRun.Passed`), a conversation when all its repeats pass, and a run counts its conversations that passed.
Every one of those sums is a method or a property on the run's records, which the pages ask (ADR 0123).

A run is one JSON file in the site's data folder, written by `RunStore` beside itself and moved into place under a
lock. The eval routes are five, on the admin group: the evals, a start, a run at its address, a stop, and an eval's
runs. The run going is held by `RunDesk`, one at a time, and its work is `RunWork`.

A replay plays the eval's last live run back from its recording, the judge's answers included, so it calls no model.
The recording is kept per play, under `{run id}/{conversation}.{repeat}`. The store appends each answer to its
play's index (`ReplayStore.SaveAnswerAsync`), and only a session's opening clears an index
(`ReplayStore.StartTrialAsync`). The judge's answers are recorded and played back by `JudgeReplay`, a wrapper over
the engine's `ModelReplayChatClient`, which keys an answer by what the request asks. A reworded criterion asks
something new, so a replay of it misses and stops.

In the web, a conversation's page draws each mark with `MarkLine`, and links "the run before" as the newest earlier
run of any kind. The run's page reads the eval's run list (`RunRow`) for its foot. The framework already has a copy
to the clipboard, for a code listing (`FrameworkScripts`, `CodeListing.razor.js`). The colours the screens need are
there: the theme's blue (`--bs-info`), green (`--web-ok`) and red (`--bs-danger`).

## Design

### 1. In plain words

On a conversation's page every criterion gets a **Flip** button. Flip opens a small box under the mark: one line for
why, if you want to write one, and "Flip to met" or "Don't flip". A flipped mark turns blue. It says what you
flipped it to, what the judge said, and your note, and it has **Undo the flip**. From then on your answer counts
in its place: in whether the turn, the conversation and the run passed, and in every count. Facts can't be flipped,
since code tells them.

On a run's page that has ended, **Re-grade** makes a new run from the run's stored answers. No agent is asked. The
facts are told again in code, which is free. A mark is kept, with your flip and note, wherever its criterion's words
and the agent's answer are the same as before. The judge is asked only for a criterion that is new or reworded, and
its answers go into the live run's recording, so Replay free plays again afterwards. The re-graded run says what
changed in the file and what it did, how many judge calls it made, and what they cost. It starts at once, with no
ask.

A replay carries your flips too: where the agent's answer and the criterion are the same as in the live run it
plays, the live run's flip comes along.

Every run is compared with the run before it: a live run or a replay with the newest earlier run of the eval that
finished, a re-grade with the run it re-graded. The run's page says "▲ 1 more than the run before" and tags each
conversation that now passes or now fails. The evals' card says the same in one line. Under the run's conversations,
**The last 8 runs** draws how many passed in each, and lists the criteria missed most, with how often you flipped
each one.

**Copy as conversation**, on a conversation's page, copies the conversation as a block for the eval file, ready to
paste and change.

### 3. A flip, on its mark

![The types: a flip on a mark, the run's records asking which answer counts, the same-answer rule, the re-grader, the comparison and the history, the routes and the pages](diagrams/F126.4-flips-re-grade-and-better-or-worse-interface-design.svg)

A mark gains your flip. It is an init property, absent on every run kept so far, so their files still read. The
mark is then asked which answer counts: the judge's, or the other one when you flipped it.

```csharp
public sealed record Flip(DateTimeOffset At, string? Note = null);

// Mark gains
public Flip? Flip { get; init; }
public bool CountsAsMet();               // Met, or the other answer when flipped
```

Every sum on the records asks `CountsAsMet()` instead of `Met`: a repeat's `Passed`, its counts and its first miss.
A repeat and a run count their flips (`CountFlips()`), and a conversation says when it passed only because of a flip
(`PassedAfterAFlip()`). A run's page lists the failed first, then those, then the rest. A run makes a copy of itself
with one mark flipped or put back (`WithFlip`), or none when it has no such mark.

The flip is set at the mark's own address, and put back with a `DELETE` at the same one:

```
PUT    /v1/admin/evals/runs/{id}/{conversation}/{repeat}/{turn}/criteria/{criterion}/flip   { "note": "…" }
DELETE /v1/admin/evals/runs/{id}/{conversation}/{repeat}/{turn}/criteria/{criterion}/flip
       204 done · 404 no such run or mark · 409 the run is going · 400 a note of more than one line
```

The turn and the criterion are counted from 1, as the pages show them. A run that is going can't be flipped, since
its file is being written. The store changes a run under its lock, reading and saving in one go
(`RunStore.Change`), so two flips at once can't lose one. The page reads the run again after each (ADR 0042).

### 4. The same answer keeps the same mark

One rule decides when a mark carries over, and both a re-grade and a replay ask it. A turn's transcript says the
same as another when its ask, its answer, its error and each tool call (the tool, what it was sent, what it gave
back, whether it failed) are the same. The time it took doesn't count. Where two turns say the same and a criterion's
words are word for word the same, the earlier mark is the mark, with its flip and its note.

```csharp
// TurnTranscript gains
public bool SaysTheSameAs(TurnTranscript other);

public static class MarkReuse
{
    public static Mark? FindReusable(TurnRun before, TurnTranscript now, string criterion);
    public static RepeatRun CarryFlips(RepeatRun played, RepeatRun? live);
}
```

A replay plays the live run's repeats, so the runner is handed that live run, which the route already reads to
start a replay. After each repeat is graded it carries the live run's flips onto it.

### 5. Re-grade

![The parts and the steps: the contracts, the eval library with the re-grader, the eval routes, the recordings, and the web's pages](diagrams/F126.4-flips-re-grade-and-better-or-worse-architecture.svg)

```
POST /v1/admin/evals/runs/{id}/regrade      202, Location: the new run's address
                                            404 no such run, or its eval is no longer here
                                            409 a run is going · 400 no data folder
```

A re-grade is a run of a kind of its own, `re-grade`, which names the run it re-graded (`RegradeOf`) and the live
run its answers came from (`ReplayOf`). It goes through the desk like any run, one at a time, and Stop stops it.

```csharp
public sealed class Regrader(Judge judge, TimeProvider clock)
{
    public Task<EvalRun> RegradeAsync(EvalRun started, EvalRun graded, EvalFile file,
        Func<EvalRun, Task> kept, CancellationToken cancellationToken);
}
```

It goes through the eval file as it is now. A conversation the graded run doesn't have, or whose asks are not the
same, is left out, since no answer to it is stored, and the re-graded run says so. For each repeat of the rest it
tells every fact again from the stored transcript, keeps every mark `MarkReuse` finds, and asks the judge for the
other criteria. The judge's calls are recorded under the live run's play, `{live run}/{conversation}.{repeat}`, by
`JudgeReplay` in its recording mode. The store appends them beside the old answers, so a replay of that live run
finds them. That is VCR's `new_episodes`.

A re-graded turn's agent cost is a known 0, since no agent was asked. Its judge cost is what its new judge calls
cost, and a kept mark costs a known 0. A judge that can't mark ends the re-grade as could not finish, as it ends a
run.

### 6. Better or worse

![A criterion reworded: the person flips a mark, re-grades the run, and Replay free plays the new criterion back](diagrams/F126.4-flips-re-grade-and-better-or-worse-communication-a-criterion-reworded.svg)

A run is compared with another by a method on the run, and the answer is a record:

```csharp
// EvalRun gains
public RunChange CompareWith(EvalRun before);
public IReadOnlyList<CriterionTally> TallyCriteria();

public sealed record RunChange(int PassedBefore, int PassedNow, IReadOnlyList<string> NowPass,
    IReadOnlyList<string> NowFail, IReadOnlyList<CriterionChange> Criteria, int CriteriaKept,
    IReadOnlyList<string> LeftOut);
public sealed record CriterionChange(string Conversation, int Turn, string Criterion, bool Added);
```

Which run is "the run before" is asked of the eval's run list, as the rows have it:

```csharp
public sealed record CriterionTally(string Text, int Missed, int Flipped);   // in how many runs

// RunRow gains
string? RegradeOf, IReadOnlyList<CriterionTally> Criteria                    // each 0 or 1 on one run's row

public sealed record RunHistory(IReadOnlyList<RunRow> Rows)
{
    public RunRow? FindBefore(RunRow run);              // the run it re-graded, else the newest earlier finished
    public IReadOnlyList<RunRow> FindLastFinished(int count);
    public IReadOnlyList<CriterionTally> TallyMissedMost(int count);
}

// EvalRow gains
RunRow? RunBefore, int? CountChange()
```

A run that stopped or couldn't finish holds only part of its conversations, so it has no run before and is never
one. The API fills each run's row from the run it already reads to make the list, and the eval's row with its run
before, so nothing is read twice. The run's page reads the run before whole, to tag what now passes or fails.

The conversation's page links the run before by the same rule, which changes today's link: it took the newest
earlier run of any kind.

### 10. What is reused

No new package and no new project. The flip is stored by the run's own JSON and the store's lock. The re-grade
reuses `Facts`, the `Judge`, `JudgeReplay` and the store's appending, and runs on the desk with its stop. The
comparison is methods on the records, as every sum of a run is. The copy uses the eval file's own options and
reader, and the framework's copy to the clipboard. The colours are the theme's names, and the layout is Bootstrap's
classes.

### Step 5: the same answer keeps the same mark, and a replay carries the flips

The tests come first. Two transcripts with the same ask, answer, error and calls say the same, whatever time they
took, and one changed word in any of them, or a call more, makes them differ. `FindReusable` gives back the earlier

## Verification

Every step's tests are named in it. Before the pull request, `main` is merged in and the full suite runs in the pull
request's checks, with Core's rule tests run here first. One paid re-grade, in step 12, on Louis's go. Free and by
hand: step 12's replay, flips and copy, and the looks of steps 4, 9 and 10.

**Done when:** a person flips a criterion with a note and undoes it, and the run's numbers follow; a re-grade makes
a new run from a run's answers, asking the judge only for what changed, and says what it did; Replay free plays a
reworded criterion after one re-grade; a replay keeps the live run's flips where the answer is the same; every run
says how it compares with the run before, and the run's page shows the last 8 runs and the criteria missed most;
and a conversation copies as a block that reads back into the eval file.

**Two new lines for ADR 0134, approved with the plan.** Under *Decision*: "A flip is kept on its mark, and a re-grade or a
replay carries it where the criterion's words and the agent's answer are the same." And: "A re-grade is a new run
made from a run's stored answers: facts told again, a mark kept where the criterion and the answer are the same, the
judge asked only for the rest, and its answers added to the live run's recording, so a replay plays them back."
They go into the ADR in step 13.
