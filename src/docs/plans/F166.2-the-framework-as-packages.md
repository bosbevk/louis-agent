# F166.2 The framework as packages

A plan: the 31 framework projects Puls builds on are published as NuGet packages to GitHub Packages, each released
by its own tag, so a project outside this repository builds an agent from packages alone. It is the second child of
[F166 Puls in its own repository](F166-puls-in-its-own-repo.md). This file says what is built and why, then gives
its eight steps.

## Context

F166 moves Puls to its own repository, on the framework as published packages (Louis's pick C, 2026-11-19). F167
first gave every project one name, so a package, its DLL and its namespace read the same (ADR 0129). Louis's picks
for this child, 2026-11-21, each of three options after research:

| # | The choice | His pick |
|---|---|---|
| 1 | Where the packages are published | C: GitHub Packages now, nuget.org at the first stable `1.0` |
| 2 | How a version is made | A: MinVer, from git tags |
| 3 | Which projects | C: the 31 Puls reaches, each on its own version |
| 6 | How a release treats its neighbours | Updated A: one tag per package, as OpenTelemetry .NET contrib does; tags of packages that belong together pushed together; a guard refuses a package whose framework dependency isn't on the feed |

**What was looked up.** The 31 are read from the references of Puls's 26 projects: nine of the engine, four of the
evals, five hosts, five of the web, six general packs, and the two test helpers. 25 are plain libraries, three are
Razor class libraries (`LouisAgent.Web`, `.Web.Accounts`, `.Web.Evals`, whose scripts and styles travel as static web
assets), and three are on ASP.NET's shared framework. The two test helpers say `IsPackable=false` today. No project
sets a version, and there is no `Directory.Build.props`.

GitHub's docs: the NuGet registry supports package-level permissions; a package published from a workflow with
`GITHUB_TOKEN` "inherits the visibility and permissions model of the repository", and this repository is public; a
workflow in another repository reads a package when the package grants that repository access; and "in most
registries, to pull a package, you must authenticate ... regardless of whether the package is public or private", so
even Puls's restore carries a token. MinVer's docs: a tag prefix per project versions each on its own, with
`MinVerIgnoreHeight` "often useful if you are versioning multiple projects in a single repository independently",
and a clone deep enough to see the tags (`fetch-depth: 0`). NuGet's docs: "Project to project references are
considered by default as NuGet package references".

**Not known yet, said plainly.** The version range a project reference becomes in a package, and how MinVer treats a
project that references one with another prefix: the docs read don't say. Step 3 proves both on a real pack, and the
plan stops there if either doesn't hold. Whether Puls's own `GITHUB_TOKEN` restores from this repository's feed with
no grant, since both repositories are public: step 7 proves it.

**Put to Louis with this plan, each with the one recommended.** Three small choices the picks leave open:

- *The tag's shape.* `LouisAgent.Core-0.1.0`, the package's name, a dash, its version, as OpenTelemetry .NET contrib
  writes `Instrumentation.AWS-1.0.0` (recommended); or `core-v0.1.0`, shorter but a second name to keep; or
  `LouisAgent.Core/v0.1.0`, which some tools read as a folder.
- *The first version.* `0.1.0` for all 31 (recommended), since nothing is stable before `1.0` (ADR 0049); or each
  from `0.0.1`; or `1.0.0`, which would mean moving to nuget.org at once by pick 1.
- *Where the shared settings live.* One `Directory.Build.props` at the root, `IsPackable` false by default and true
  only in the 31 (recommended, Microsoft's way of sharing build settings); or a props file each package imports by
  hand; or every setting written in each of the 31.

## Design

### 1. A package is a project's settings

No C# type is added. The root's `Directory.Build.props` says what every package carries: `IsPackable` false unless a
project says otherwise, the licence by its SPDX name (`PolyForm-Noncommercial-1.0.0`, ADR 0127), the repository's
address and the author, Source Link so a reader can step into the source, and MinVer for whatever is packable. Each of
the 31 says `IsPackable` true and its own tag prefix. A rule test holds the list.

![The shared props, a package's own two settings, the rule test that holds them, the consumer test and the publish workflow](diagrams/F166.2-the-framework-as-packages-interface-design.svg)

### 2. From a tag to the feed

![A tag starts the publish workflow, which packs that one project, guards its dependencies and pushes it to GitHub Packages, where a clean project and Puls restore it](diagrams/F166.2-the-framework-as-packages-architecture.svg)

A version tag is pushed by Louis, as every push is. The workflow packs only the project the tag names, checks that
each `LouisAgent.*` package it depends on is on the feed at the version it names, and pushes it with the workflow's
own `GITHUB_TOKEN` (`packages: write`). Tags of packages that belong together are pushed together; the workflow
publishes them in the order they depend on each other.

![One tag: GitHub starts the workflow, MinVer gives the version, each framework dependency is checked on the feed, then the package is pushed](diagrams/F166.2-the-framework-as-packages-communication-one-release.svg)

![Packing LouisAgent.Web: its DLL, its static web assets, its licence, and its framework dependencies at the versions they had](diagrams/F166.2-the-framework-as-packages-objects-in-memory.svg)

### 3. The namespace map

| Type or file | Folder | Step |

| `LouisAgent.Packages.IntegrationTests`, `ConsumerBuildsAnAgentTests` | `src/tests/packages/`, `LouisAgent.Packages.IntegrationTests` | 3 |
| `publish-packages.yml` | `.github/workflows/` | 4, 5 |
| `consume-packages.yml` | `.github/workflows/` | 7 |

### 4. What is reused

MinVer (Apache-2.0, Louis's pick 2) is the one new package, a build-time one that ships inside nothing. Source Link
comes with the .NET SDK. Packing is `dotnet pack`, pushing `dotnet nuget push`. The consumer test runs the `dotnet`
CLI with its arguments as data (ADR 0004), as the starter's integration tests run `dotnet new`. The release follows
`deploy-sites.yml`'s shape for a workflow that writes.

## Steps

Each step is one commit with its test, written first and seen failing on an assertion. Stop after each for Louis's
review. A step that meets a choice this plan does not settle stops and puts it to him.

### Step 1: the plan is kept

Docs only: this plan, its four pictures, and its rows in the plans' index, the TODO and the work log.

### Step 2: the 31 say they are packages

`Directory.Build.props` and the two settings in each of the 31; MinVer added. **Test first:** `PackagesTests` says the
31, and no other project, are packable, each with the prefix of its own name and a dash, and that the props name the
licence by its SPDX name.

### Step 3: a clean project builds an agent from packages

The proof the plan rests on, before anything is published. **Test first:** an integration test packs the 31 into a
folder at version `0.0.0-local`, writes a small project in a temporary folder that references only `LouisAgent.Core`
and `LouisAgent.Testing` from that folder, and builds and runs it: an agent answers through the fake chat client.
The test also reads one package's `.nuspec` and records the range a project reference became. If the range or
MinVer across prefixes doesn't hold, the plan stops and goes back to Louis.

### Step 4: the publish workflow

`publish-packages.yml`, on a tag `LouisAgent.*-*`: it checks out with its tags, packs the tag's project, and pushes it
with `GITHUB_TOKEN`. **Test first:** a rule test reads the workflow and finds its trigger, its `packages: write`, its
`fetch-depth: 0`, and that it packs only the tag's project.

### Step 5: the guard

Before the push, the workflow reads the package's framework dependencies and asks the feed for each at its version;
one missing stops the run, naming it. **Test first:** the same rule test finds the guard before the push.

### Step 6: the first release

On Louis's word, the 31 tags at `0.1.0`, pushed together. The workflow publishes them in order. Their pages on
GitHub show the licence and link to the repository. No code changes; the step records the run.

### Step 7: Puls's side, proved from here

`consume-packages.yml`, run by hand: the clean project of step 3 restores from GitHub Packages with only the
workflow's `GITHUB_TOKEN`, and builds. It is the done-when, and what F166.3 copies into the `puls` repository.

### Step 8: the docs, and the close

A guide, *Publish the framework*, for tagging and releasing; the projects' index and the repo map; the decisions
that later work follows put to Louis as an ADR; the write-up; the records; this plan folded and deleted.

## Verification

The rule tests hold the 31 and the workflows' shape. The integration test of step 3 packs, restores and runs an agent
from packages on every pull request. The first release (step 6) and the restore from the feed (step 7) are checked
by their runs on GitHub. No paid run.

## Concepts, and where they sit in GOAL.md

- **Publishing a framework** (steps 2 to 6): a package as a project's settings, a version from a tag, a guard before
  a push. *Skill 18, testing and shipping.*
- **A product on a framework** (steps 3 and 7): a project outside the repository built from packages alone, which is
  what Puls becomes. *Skill 20, extensibility.*
