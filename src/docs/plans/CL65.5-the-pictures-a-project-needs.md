# CL65.5: The pictures a project needs, and where they stand

> **Plan.** The last child of [CL65](CL65-the-diagrams-as-an-engine.md). Which pictures a project's doc must show
> is decided by what kind of project it is and by what it needs of its own. Each picture stands beside the text
> it explains, and no doc keeps its pictures in a section apart.

**Status:** approved 2026-11-14 with its parent (Louis: "approve go unattended"), his pick of three made that
day ("3."), and built unattended on his word of 2026-11-15: "finish on your own then merge, tell me only when
you reach 134.1 again".
**Branch:** `feature/F134.1-the-start-is-a-stage`.

## Context

Louis, 2026-11-14, while the picture builder was built:

- "the project type and requirements must drive which diagrams is required"
- "if diagrams is missing add them"
- "graphs must also be placed where it is used ort needed not a section"

His pick of three: the project's kind sets a floor, and its own requirements add to it. A fixed table gives each
kind of project its required diagrams, a doc names what it adds, and a test holds both. The floor put to him,
which he did not change: every project an overview and a class diagram; a library with a main path an activity
and a sequence diagram; a host or a program a sequence and a deployment diagram; a web app or a Razor library a
component diagram; a console tool an activity diagram.

**What was looked up.**

- *The rule today.* `DocsDiagramsTests.EveryProjectDoc_ShowsItsFourDiagrams` asks every project doc for the same
  four kinds: cards, flow, sequence, classes. `EveryProjectDoc_ShowsItsOverview` asks for the overview by name.
- *The docs.* 42 project docs: 25 the framework's, 9 the packs', 8 the demos'. 35 open with a `**Kind:**` line in
  free words ("class library (`net10.0`)", "library, ASP.NET Core minimal API"), and 7 open with an
  *Explanation* line and name no kind.
- *What they show,* by the type each picture states since CL65.3: every doc an overview, a class diagram and a
  sequence. For how it works, 32 show a component diagram and 10 an activity diagram, one of them both.
  `tests` shows a package diagram, core a composite structure, the web a nested picture. No doc shows a
  deployment diagram.
- *Where the pictures stand.* 39 docs have a `## Diagrams` section, holding 109 pictures between them.
- *The "component diagram" of the floor* was said when the `components` kind was every doc's word for it, and
  Louis's "all projects which has components should have an component diagram". That kind is `nested` since
  2026-11-15 and its type is a composite structure. So a web project's floor is a composite structure diagram,
  drawn as a nested picture of a main component.
- *Who names the old rule:* the guide and the skill for drawing a diagram, the projects' index, and
  `.claude/rules/docs.md`, which lists *Diagrams* among a project doc's shared sections.

**What could not be confirmed** before the build: which libraries have a main path and which only hold
contracts. Step 2 reads each doc and says.

## Design

**A doc states its kind in its `**Kind:**` line, from a fixed list.** The first words of the line are the kind,
and what follows in brackets is free: `**Kind:** library (`net10.0`)`. The seven docs with no such line get one.

| Kind | What it is | Its floor |
|---|---|---|
| `library` | A class library with a main path | overview, class, activity, sequence |
| `contracts library` | A library of contracts or content, with no path of its own | overview, class |
| `host` | A library a program adds to serve the agent: the API, the CLI, ACP, MCP, accounts | overview, class, sequence, deployment |
| `program` | A console app that composes and runs | overview, class, sequence, deployment |
| `web app` | A Blazor WebAssembly app | overview, class, composite-structure |
| `Razor library` | A Razor class library | overview, class, composite-structure |
| `console tool` | A developer's tool, run by hand | overview, class, activity |
| `test projects` | The doc of the test projects | overview, class |
| `content` | Files an agent reads, such as runbooks | overview |

**A doc names what it adds** in the same line: `**Also shows:** `component`, `deployment``, by the names a
picture's `type` has. A doc shows exactly what its floor and its own list ask for, no less and no more, so the
line is a true statement of the doc's pictures.

**The missing pictures are drawn from the code.** Where a floor asks for a picture the doc lacks, it is added:
about 19 activity diagrams, 8 deployment diagrams and 5 nested pictures. Every box is one the code or its
compose file has. While they are added a test holds the list of what is still missing, and the list only
shrinks. With it empty the test is a plain rule.

**No doc has a *Diagrams* section.** Each picture moves beside the text it explains: how it works and the main
case inside *How it works*, the class diagram beside the types it shows, a deployment diagram beside where the
project runs.

**The knowledge is on named types** (ADR 0123), in the docs' tool's tests, since only a test asks: what kinds
there are, what each asks for, and what a doc states and shows. The guide's table is held equal to the floor
by a test.

## Steps

One commit each, test first where a rule changes. Unattended.

1. **The plan**, its four pictures and its row in the plans' index. *Test:* none (docs).
2. **Every project doc states its kind.** `ProjectKind`, `ProjectDoc`. *Test:* every project doc's kind line
   starts with a kind of the list, seen failing first. The 42 lines are written.
3. **The floor, and a doc's own list.** `ProjectFloor`, `**Also shows:**`. *Test:* a doc shows exactly what its
   floor and its own list ask for, with a ratchet for what is still missing. It replaces the four-kinds rule.
   The guide's table is held equal to the floor.
4. **Where a host and a program run:** their deployment diagrams, from the compose files and the programs.
5. **What a web project's main component is made of:** the nested pictures.
6. **The engine's main paths:** activity diagrams for the framework's libraries and the console tool.
7. **The packs' and the demos' main paths:** their activity diagrams. The ratchet is empty and becomes a rule.
8. **No *Diagrams* section.** *Test:* no project doc has one, seen failing on the 39 first. Each picture moves
   beside its text. The guide, the skill, the index and the docs' rules follow.
9. **Documented and done.** The write-up, the work log, the TODO, this plan deleted, and CL65 closed.

## Concepts

- Steps 2 and 3: a rule a person states once in a table, and a test that reads the same table. Skill 18
  (testing and shipping).
- Steps 4 to 7: a picture is a claim about the code, so it is drawn from the code. Skill 17 (observability of
  a design) and skill 20 (extensibility), for what each kind of project owes its reader.
